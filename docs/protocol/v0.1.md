# Anamnesis v0.1.60

*(formerly "Phaedo Protocol" — see §1.4; "Phaedo Protocol" is retained as a v0.x alias, and Phaedo is the reference implementation of Anamnesis.)*

> **Changes since v0.1.59 (2026-07-24) — §10.5 gains `revoked` tombstones, because REVOKING a guardrail did not work.** The v0.1.55 fix made guardrail sets survive a sync by reconciling them as a **union** — the right call, since the bug it fixed silently DELETED the subject's explicit decisions. But a union cannot express a deletion, and nothing in the design noticed: removing a rule on one device dropped it locally and the other device's copy put it straight back on the next sync. The reference implementation has shipped a Remove button on that form throughout, so **every revocation performed to date silently failed** if a second device held the rule. This is the inverse of the v0.1.55 defect and strictly the worse direction — that one lost a guardrail the subject wanted, this one keeps an `autoproceed` the subject explicitly took back, and §8.3 now mints payment credentials against exactly those grants. A policy document MAY now carry `revoked`, a list of tombstones naming removed rules; consumers MUST drop a tombstoned rule and merges MUST union tombstones from both sides, so a revocation propagates even to a device that never saw the removal. Deliberately **fail-closed** (a tombstoned id stays dead even if the rule reappears from a restored backup), with identity computed the same way the merge dedupes so a tombstone cannot miss its target, and **capped by count, never pruned by age** — an age-pruned tombstone is a resurrection waiting for a stale device. Enforced at both consumer reads: the resolver (`normalizePolicies`) and, more importantly, the §12 AP2 mandate builder, where a surviving revoked grant would be signed into a payment credential. **Reference:** `sync-merge.js` / `mobile/src/lib/syncMerge.ts` (`mergeConsultPolicies`, now runtime parity-tested — the phone-side merge previously had no test at all, which is how this survived), `popup.js` (`removeGuardrail` writes the tombstone), `mcp/consult-policy.js`, `mcp/ap2.js`. Locked by `scripts/test_guardrail_sync.mjs` (14), `scripts/test_mobile_sync_merge_parity.mjs` (18, new), `mcp/test-ap2.mjs` (58), `mcp/test-consult-policy.mjs` (155). `phaedo_protocol_version` stays `0.1`.

> **Changes since v0.1.58 (2026-07-24) — §8.3 gains conformance vectors (TC-SIGN) and a signing-audit record; `asymmetric_signatures` deliberately STAYS false.** The signing ceremony is now wired end to end (enclave keygen/sign, key publication over the pairing, the sign-request transport, the phone signing sheet, and the `phaedo_sign_mandate`/`phaedo_sign_status` tools). Two things land here. **(1) TC-SIGN** publishes verify-direction known-answer vectors for ES256 (`spec/test-vectors/signing.json`): ECDSA signing is randomized, so — exactly like TC-ENV — a conforming *verifier* must reproduce each `expect_verify`, and a producer proves the sign direction by round-tripping its own output. `conformance.json` reports `TC-SIGN: pass`, enforced by the §11.3 tie. **(2) A signing audit** — minting a credential is recorded, but NOT as a §10.6 consultation receipt (a signature has no signal and must not feed the act-as-me learning loop or the agreement metric); it is its own encrypted, domain-separated append-only log holding a digest of the signed bytes plus coarse metadata, never the mandate content or the signature. **What deliberately does NOT change: `optional_features.asymmetric_signatures` stays `false`.** That flag declares a *producer* capability the reference implementation exercises, and two things are still true — the reference fingerprint producer does not emit the `signatures` field (it remains `maxItems: 0` / MUST NOT populate), and the on-device biometric signing *ceremony* has not yet been exercised end-to-end on hardware. "TC-SIGN passes" (verification conforms) and "asymmetric_signatures is false" (we do not yet emit signatures) are both true and not in tension. The flag flips when the ceremony is hardware-verified and a producer emits signatures — the same "verified on hardware before claiming" discipline that caught the enclave's algorithm mismatch and the verifier's low-S default earlier in this arc. **Reference:** `spec/test-vectors/signing.json`, `mcp/signing-audit.js`. `phaedo_protocol_version` stays `0.1`.

> **Changes since v0.1.57 (2026-07-23) — §8.3 asymmetric signing specified: ES256, and the algorithm changed because CUSTODY outranks it.** §8.3 was three sentences naming Ed25519 and deferring everything else; OQ9 recorded Ed25519 as "confirmed for v1.0". Both are revised to **ECDSA P-256 / SHA-256 (ES256)**, and the reason is the interesting part. The requirement that actually matters to a third-party verifier is not which curve was used but that the signing key is **non-extractable in a secure element** — a signature asserts the subject's trust anchor produced the artifact, and a key ordinary application code could read cannot support that assertion. The iOS Secure Enclave holds **P-256 only** and cannot hold an Ed25519 key at all, so the previously-specified algorithm was not co-buildable with the property the signature exists to convey. ES256 costs nothing in interop (a first-class W3C VC / JOSE suite). **Verified on hardware BEFORE specifying** — a Secure Enclave key was generated, used to sign, and the signature checked against the exported public key on a real device; this section describes something that was demonstrated, not intended. Three further constraints are now normative: the key is **device-bound** and MUST NOT ride a §8.2 backup (a replacement device establishes a NEW identity and republishes — identity is re-established, never transported, the same boundary §8.2 draws); the signing input is the **§6 RFC 8785 canonicalization with `signatures` omitted**, mirroring the §8.2 bootstrap `digest` construction; and **key discovery for an UNPAIRED verifier is explicitly NOT specified** rather than hand-waved — publication, attestation and revocation are unresolved, which honestly bounds §8.3 to parties that already share state, the employer scenario in the section text included. **Nothing is emitted yet:** `signatures` stays `MUST NOT populate` (enforced as `maxItems: 0` in `fingerprint.schema.json`), `conformance.json` keeps `asymmetric_signatures: false`, and the entry shape plus signature encoding are deliberately deferred until a consumer emits one, so the wire form is settled by a real use. **Reference:** `mobile/modules/phaedo-signing` (Secure Enclave keygen/sign), `mobile/src/lib/p256Verify.js`; scope + the decision record in `docs/roadmap/asymmetric-signing-scope-2026-07-23.md`. `phaedo_protocol_version` stays `0.1`.

> **Changes since v0.1.56 (2026-07-22) — §8.2 backup mode reconciled to the shipped recovery-code model (documentation only; the wire object is unchanged).** The §8.2 backup-mode prose still described the pre-implementation design — an artifact re-sealed under the **master key**, its HMAC proving "a holder of the master key." That was never buildable for the feature it exists to serve. The vault device holds its key material in non-extractable hardware, so that key does not survive the device; a lost-phone backup sealed under it could never be opened on the replacement, which is precisely the moment recovery is needed. The shipped implementation (increment 1, 2026-07-19, owner-approved) is instead **zero-knowledge and user-custodied**: the artifact is sealed under a freshly generated 160-bit **recovery code** the subject alone holds and the producer never retains, HKDF-derived into two domain-separated sub-keys (`phaedo:export:backup:v0.1` for the AES-256-GCM envelope, `phaedo:export:hmac:v0.1` for the tag), with no escrow — losing both the code and the backup is unrecoverable, the accepted end of a no-cloud, no-accounts, keys-never-leave-the-device design. This entry updates the spec to match what shipped: the `mode:"backup"` object shape, the `phaedo:export:hmac:v0.1` context, and the HMAC-before-GCM restore order are all **unchanged**, so no conforming producer or consumer changes — only the described key source (recovery code, not master key) and the security claim it carries (proof of the recovery-code holder, not the master-key holder). Device-to-device transfer where both ends already share key material remains §8.4's encrypted-seed rendezvous, not backup mode. **Reference:** `mobile/src/lib/backup.ts` (`buildBackup`/`restoreBackup`, `deriveKeys`), `mobile/src/screens/BackupScreen.tsx` + `RestoreScreen.tsx` (#154, #155). `phaedo_protocol_version` stays `0.1`.

> **Changes since v0.1.55 (2026-07-22) — §10.2 published domain vocabulary (additive; free text stays valid).** `domain` is free text the AGENT chooses, and §10.5 matching, the §10.6 receipt and §10.7's approval counts all key on it verbatim — so two spellings of one concept become two classes and the subject's evidence splits between them. Observed in the reference deployment as `financial` ×16, `finance` ×26 and `finance.crypto_trading` ×1 for a single domain, with 7 approvals split 3/4 so **neither class reached §10.7's threshold of 5**: the promotion channel was starved by vocabulary drift rather than by the subject's actual behaviour. `spec/domains.json` now publishes 17 canonical terms with their aliases, and a resolver resolves a domain to its canonical term before recording it as evidence. **Free text remains valid** — an unrecognized domain is recorded and matched exactly as before; this confers identity, it is not an enum and not a gate. Three constraints keep it from becoming one. **(1) Aliases are SYNONYMS, never GENERALIZATIONS.** An alias asserts the same concept at the same risk; a child→parent mapping is forbidden, because a grant authored for the general class would silently cover a narrower, riskier one the subject never demonstrated. Hence `investing` is its own term rather than a `finance` alias — a spending guardrail and a trading guardrail are not the same authority — and `crypto_trading` is absent entirely, so it does not merge. Same defect that made dotted-suffix stripping unsafe in v0.1.55. **(2) The vocabulary is PUBLISHED.** The alternative, a synonym table inside the resolver, would put decision semantics where the subject cannot read it and a third party cannot reproduce it; the reference implementation embeds a copy for packaging (the npm `files` whitelist excludes `spec/`) and a test asserts the two cannot drift. **(3) Canonicalization is bounded by where it can do harm — the load-bearing rule.** §10.5 domain matching gains a canonical-equality path *for restrictive effects only*; `autoproceed` and `bias_bold` keep matching on the literal string. An alias may therefore widen a **guardrail's** reach but never a **grant's**, so a mistaken entry costs an unnecessary question rather than unearned autonomy — and because the new path is purely additive, no guardrail that fires today can stop firing. A resolver publishing no vocabulary implements the substring rule alone and remains conforming. **Reference:** `spec/domains.json`, `mcp/lib/domain.js` (`normalizeDomain` vs `canonicalDomain`, deliberately distinct), `mcp/consult-policy.js` (`domainCovers`). Locked by `mcp/test-domain.mjs` (325). **Not done:** the §4.2.7 signal-domain axis (`domainMatches` in `consult-core.js`) and the escalation push policy still match by substring — different axes, neither implicated in the evidence split, and each wants its own argument. `phaedo_protocol_version` stays `0.1`.

> **Changes since v0.1.54 (2026-07-22) — §10.7 scopes a proposed grant to the client that EARNED it (step 5; additive, narrowing).** Until now a promoted `autoproceed` was client-agnostic: one paired client demonstrated a pattern and *every* paired client inherited the resulting autonomy. That was the honest behaviour while `agents` was unenforceable, and it stopped being honest the moment v0.1.53 made scoping real and device-side authoring landed. §10.7 now reads the SERVING `client_id` recorded on each §10.6 receipt — never the self-asserted `agent_id` — and emits `agents` listing the clients whose approvals earned the class. **Strictly narrowing:** a client that contributed nothing no longer inherits the grant, and one that contributed approvals which cannot be attributed is simply left out, so it keeps asking. **The absent/empty distinction is load-bearing here and is stated normatively:** when NO contributing receipt carries a `client_id` — every receipt written before v0.1.53 — the field MUST be **omitted**, not written as `[]`. Absent means unscoped (the prior behaviour, correctly preserved for historical evidence); `[]` is a scope naming no client and would stage a grant that can never fire. **An endorsing consumer MUST carry `agents` through to the authored rule verbatim.** The reference implementation did not, and it is fixed here: `rule-review.js endorseAuthorization` rebuilt its entry field-by-field and silently dropped the scope, turning a scoped proposal into an unscoped authorization at the one write that grants autonomy — the same dropout class as `require_binding` in v0.1.48, in the same direction (a declared boundary quietly not applied). Note the limit this cannot cover: a consumer re-asserts `effect`, `require_binding` and `expires_at` at the write because it knows what they must be, but it cannot re-assert a *scope it never saw*, so a deposit that strips `agents` in transit is undetectable at the merge boundary. The card text says the grant is limited without printing an opaque `c_…` the subject cannot recognise — only the device holding the client registry can name it. `evidence` additionally records `client_count` and `unattributed` as audit provenance, distinct from the enforceable scope. **Reference:** `mcp/autonomy-promotion.js`, `rule-review.js`; `suggested_rules.agents` declared in `fingerprint.schema.json`. Locked by `mcp/test-autonomy-promotion.mjs` (68) + `scripts/test_rule_promotion.mjs` (58). `phaedo_protocol_version` stays `0.1`.

> **Changes since v0.1.53 (2026-07-22) — §10.5 `agents` hardening: four defects found by an adversarial pass on the enforcement that shipped hours earlier.** All four failed in the WIDENING direction or aborted the consultation, which is why they are worth a version rather than a patch note. **(1) ABSENT ≠ EMPTY.** The first cut collapsed a missing `agents` and `agents: []` into the same value, so an authoring surface where the subject deselects every client would have silently granted **universal** autonomy — the exact inverse of the expressed intent, and precisely the direction §10.5 exists to prevent. Omitting the field now means unscoped; `[]` is a scope that names no client and matches none. This is normative because step 4 (device-side authoring) is about to write these values. **(2) Non-string entries were COERCED.** `String()` turned `[null]` into a scope matching the literal `"null"` and `[42]` into one matching a client whose id is `"42"` — type confusion that invents principals. Entries are now type-checked and dropped, matching how every other field in the rule normalizer is handled; a list of pure junk collapses to an empty scope, which matches nobody rather than widening to everybody. **(3) The gate could THROW.** `agentScopeSatisfied` dereferenced `agents.length` unguarded, so a hand-built policy object reaching the exported `matchAuthorization`/`applyPolicies` raised a TypeError that aborted the whole consultation instead of failing inert — a fail-UNSAFE break of the resolver's stated never-throws contract. It is now defensive in the shape `require_binding` already used, and a malformed (non-array) scope fails **closed** for a relaxing effect while still being unable to disable a restrictive one. **(4) A client-scoped grant leaked into the §12 AP2 profile.** `authorizationToIntentConstraints` carried `expires_at` and `require_binding` but silently dropped `agents`, so a grant the subject scoped to one client was serialized into an Intent Mandate as **unconditional** authority — asserted to a merchant or network, where it is least correctable. AP2 has no vocabulary for "this specific paired client", so the scope cannot be expressed; the profile now **withholds** the credential, the same way it already refuses to render a restrictive rule as a restrictive mandate. New normative rule: a scoped grant MUST NOT be exported to a format that cannot carry its scope. **Reference:** `mcp/consult-policy.js`, `mcp/ap2.js`. Locked by `mcp/test-consult-policy.mjs` (152, +17) and `mcp/test-ap2.mjs` (47, +5). `phaedo_protocol_version` stays `0.1`.

> **Changes since v0.1.52 (2026-07-22) — §10.5 `agents` is ENFORCED: scope authority to a paired CLIENT, not to a claimed agent (behavior change on a previously-inert field).** `agents` has been RESERVED since v0.1.26 for a reason that looked permanent: scoping on a **self-asserted** `agent_id` is false security, so enforcement was blocked on authenticating the agent. The unblock is that **the question was aimed at the wrong party.** A resolver serves exactly one paired client, so it never needs to *ask* who is calling — it knows who it **is**, from its own pairing record. Scoping therefore matches **the resolver's own `client_id`**, an identifier established out-of-band with the subject's second device under a user-verified SAS and revocable there. Nothing agent-supplied enters the decision, so there is no credential to forge, steal from a config file, or replay — the failure mode that makes a locally-held JWT close to meaningless between co-resident processes. **`agent_id` is correspondingly demoted in the spec to an explicitly untrusted audit label** that a resolver MUST NOT gate on — the same treatment `action_descriptor` received in v0.1.48, and for the same reason: every field the gated party authors is a story about itself. **Enforcement is NARROWING-ONLY and fail-safe**, matching `expires_at` and `require_binding` exactly: scope is checked only for authority-EXPANDING effects (`autoproceed`, `bias_bold`), so a restrictive rule keeps applying regardless — otherwise `agents` would become a way to *shed* a guardrail by running an unlisted client — and an unlisted or **unpaired** resolver makes a relaxing rule inert ("does not apply"), never broader, never an error. Two smaller points carry real weight. **Comparison is case-EXACT**: the RESERVED-era parse lowercased entries, which for opaque issued identifiers could alias two distinct clients into one principal. And a scope-inert rule is **silent** (§10.4): the `require_binding` suppression note is deliberately *not* emitted for it, because telling an unlisted client that some rule would have relaxed for a *different* client leaks the shape of the subject's other grants — a fixable omission is worth reporting, being the wrong principal is not. §10.6 receipts now record **both** identities (`client_id` beside `agent_id`), so an audit distinguishes the client that acted from the vendor string it claimed, and a disagreement between them is itself a finding. The **key-theft boundary is stated in the spec rather than left implied**: a process that has already read the pairing record *is* that client, and no scoping scheme survives that — file secrecy and phone-side revocation are the controls. **Reference:** `mcp/consult-policy.js` (`agentScopeSatisfied`), `mcp/phone-source.js` (`readServingClientId` — resolved once at startup, fail-safe to `null`), `mcp/consult-core.js` (`policyCtx`), `mcp/receipts.js`. Design: `docs/roadmap/paired-client-identity-2026-07-22.md`. Locked by `mcp/test-consult-policy.mjs` (135) + `spec/test-schemas.mjs` (170). **Not done here:** phone-side authoring of `agents` (needs a native build) and §10.7 scoping its proposed grants per-client — until that lands a promoted grant stays client-agnostic, which is the honest current behavior. `phaedo_protocol_version` stays `0.1`.

> **Changes since v0.1.51 (2026-07-22) — §10.5 `amount_lt`: the missing CEILING (additive, backward-compatible).** `match` had `amount_gt`, a **floor** — "fires above N" — and nothing to express "up to N". One missing field caused two distinct symptoms. **(1)** §10.7 could not propose autonomy for any priced class, because a money rule cannot be made safe without a cap, so the whole category was excluded by a flat prohibition. **(2)** The AP2 profile had no honest `max_amount`: it mapped `amount_gt` into AP2's spend cap, which on an `autoproceed` rule inverts the subject's meaning — it would tell a merchant the subject capped spending at exactly the figure above which they wanted *more* scrutiny. `amount_lt` fixes both. Semantics mirror `amount_gt` exactly: strictly-less, and **an action with no `amount` satisfies neither bound**. That last point is what makes a ceiling safe — an unpriced action must not slip under a cap nobody can check — and it means adding either bound can only ever *narrow* a rule, never widen it. Strict comparison is deliberate on both sides: an action exactly at a ceiling falls through to a full consultation rather than auto-proceeding. **§10.7 accordingly now proposes priced classes, but under a hard constraint:** the ceiling MUST NOT be the largest amount observed (one outlier would set the bar for everything after it) and MUST have been demonstrated at least twice — the reference uses the **second-highest** approved amount, the monetary form of the existing "spread across days, not one sitting" rule; a class with fewer than two priced approvals still cannot justify a bound and is not proposed. The popup guardrail form gains both bounds (it previously could author neither). **Reference:** `mcp/consult-policy.js` (`amountLt` + the fail-closed match), `mcp/autonomy-promotion.js` (`spendCeiling`), `mcp/ap2.js` (`amount_lt` → `max_amount`; `amount_gt` demoted to an annotation). Locked by `mcp/test-consult-policy.mjs` (121), `mcp/test-autonomy-promotion.mjs` (55), `mcp/test-ap2.mjs` (42). `phaedo_protocol_version` stays `0.1`.

> **Changes since v0.1.50 (2026-07-22) — §9.6 Stained Glass interface published (resolves OQ12; interface only, algorithm out of scope).** Enhanced privacy mode gets its **interface** — the `privacy` response block (`profile`, `producer`, `preserved`, `removed`, `signal_retention`, `reversible`), five producer guarantees, and a mechanical conformance check — while the obfuscation **algorithm** stays proprietary and permanently out of scope (Appendix A). Without this a regulated vertical (health, finance, legal) literally cannot ship to a vendor-hosted model, because it has no contract to build against. The load-bearing guarantee is **no silent downgrade**: a producer that cannot obfuscate MUST return `mode_not_supported`, never standard-mode plaintext under an enhanced-privacy flag — a silent downgrade sends exactly the plaintext the subject asked not to send. Authored §5.2 instructions must be obfuscated or omitted under this mode; the verbatim requirement is a *standard-mode* guarantee. `signal_retention` is stated plainly as a **self-assertion the suite does not verify**, rather than implying an enforcement the standard cannot provide. The reference implementation still returns `mode_not_supported` (locked by TC-INJ `T-PHAEDO-INJ-0003`); §9.6 exists so a third party can build against a stable contract. Companion design doc for OQ15 (recency decay / change-point) recorded at `docs/roadmap/recency-decay-design-2026-07-19.md` — design only, nothing built. `phaedo_protocol_version` stays `0.1`.

> **Changes since v0.1.49 (2026-07-22) — §5.7 Commitments: decision STATE, not just decision style (additive, no wire break).** The eight layers are dispositional — read the catalog and every field models *how* a subject decides, and §4.6 forbids episodic content in behavioral layers so a behavioral model never becomes a dossier. The consequence is a gap an agent acting on someone's behalf falls straight into: a consultation can return "you would be cautious here" when the true answer is "you already decided this" — already declined that vendor, on leave until the fourth, that budget is frozen. **Style without state is how a proxy contradicts the person it represents.** New **§5.7** adds a short, authored, always-expiring list of facts that should change a decision (`phaedo_fingerprint.commitments`, `spec/schemas/commitments.schema.json`). It is deliberately **not memory** — no recall, no retrieval, no history — and three constraints keep it from growing into one: **authored only** (`source` is an enum whose only member is `subject`, so an inferred commitment is a schema violation, not a convention); **deferential only** (`effect` ∈ `escalate`/`decline`/`bias_cautious` — `autoproceed` is not expressible, because being bound by something is never a reason to grant more latitude, and autonomy expansion keeps exactly one path); **perishable** (`expires_at` REQUIRED — decision state that outlives its situation blocks work forever, which is worse than not recording it). Commitments are **never injected**: their text names counterparties and amounts by nature, so it reaches the §10 consultation boundary only, and the §4.6 episodic rail deliberately does not apply to a `statement` (the same carve-out §5.3 example content gets, for the same reason). Disclosure is opt-in: `disclose` defaults false, and a resolver MUST return a generic hint rather than the statement — **the decision always crosses, the reason only when the subject said it may**. Carried on the fingerprint A-home so it syncs today with no new transport, mirroring `standing_rules`. **Reference:** `commitments.js` (shared classic module: popup + resolver), projected into the existing §10.5 rule shape by `loadPolicies`, so precedence, expiry enforcement, domain matching and the deterministic pre-flight all work unchanged; a `bias_cautious` commitment now names itself in `rationale_hint` (a generic "per your preference" would hide the only useful fact). Popup gains an authoring surface. Locked by `scripts/test_commitments.mjs` (40, new) + `mcp/test-consult-policy.mjs` (105). **Deferred:** standing budgets (OQ17) are the other form of decision state and belong in this artifact; shape deferred to the release that implements them. `phaedo_protocol_version` stays `0.1`.

> **Changes since v0.1.48 (2026-07-22) — §10.7 Autonomy Promotion: the first channel that can propose LESS friction (additive, no wire break).** Every learning channel in v0.1 can only make an agent more deferential — §10.5 forbids an authored disposition from expanding autonomy, and the delegation channel learns from *corrections*. Expanding autonomy requires the subject to hand-author an `autoproceed` authorization, which almost nobody does, so a conforming deployment accumulates friction and never sheds it. That is not only a usability failure: the 2026 approval-fatigue literature is consistent that an approval which has become reflex is neither meaningful consent nor a safety control. New **§10.7** lets a producer **propose** a §10.5 `autoproceed` authorization from a class of actions the subject has repeatedly approved — staged as a `suggested_rules` entry (`kind:"authorization"`, `source:"autonomy_promotion"`) and authored **only** by the subject's endorsement, so the authored-only invariant holds unchanged; a producer MUST NOT author an authorization or propose any effect but `autoproceed`. **Repetition is explicitly not consent:** a proposal requires spread across distinct days, ZERO rejections or modifications in the class, a high existing agreement rate in that domain over enough scored decisions, and evidence that is not batch-recorded (`user_action_at`, new optional §10.6 field — written with `user_action`, absent on older receipts, and MUST be read as "unknown" rather than "batched"). **What may be proposed is bounded:** reversible only, magnitude-capped at what was observed and never `high`, domain-scoped, `require_binding: true`, and `expires_at` set — plus a flat prohibition on proposing for any class carrying an `amount`, since §10.5 has `amount_gt` (a floor) and no ceiling, so money cannot be bounded from above. An endorsing consumer SHOULD re-assert those constraints at the write rather than trust an object that crossed a sync boundary; the reference implementation refuses to endorse a staged authorization that lost its binding requirement, expiry, reversibility, or domain scope, and the extension's merge boundary drops such a deposit before it can be shown as an endorsable card. **Reference:** `mcp/autonomy-promotion.js` (the gates), `rule-review.js endorseSuggestion` (the authored write), `sync-merge.js mergeAgentSuggestions` (transport guard), popup review card (an authorization renders as a plain statement of what is granted and for how long — there is no wording to edit, and an editable box whose edits go nowhere would misrepresent the button). Schemas: `suggested_rules` gains `kind`/`match`/`effect`/`require_binding`/`expires_at`/`note` with a conditional requirement, `source` gains `autonomy_promotion` in both homes, receipt gains `user_action_at`. Locked by `mcp/test-autonomy-promotion.mjs` (44, new), `scripts/test_rule_promotion.mjs` (54), `scripts/test_sync_merge.mjs` (68). `phaedo_protocol_version` stays `0.1`.

> **Changes since v0.1.47 (2026-07-22) — §10.2 `action_binding` + §10.5 `require_binding`: the action descriptor is untrusted input (additive, backward-compatible, no wire break).** Closes a soundness gap in the consultation gate. Every field a resolver decides on — `domain`, `reversible`, `magnitude`, `amount`, `summary` — is authored by **the agent being gated**, so an `autoproceed` authorization fires on whatever the agent *says* it is doing, and a subject answering an escalation approves the agent's prose account of the action. This is a live 2026 vulnerability class (approval shown for one target, action taken on another — CVE-2026-12958, CVE-2026-50549), and it bites Anamnesis hardest because the gate *is* the product. §10.2 now states normatively that **the descriptor is the requesting agent's claim, never a verified property**, and adds optional **`action_binding`** — `{ tool_name, arguments_hash, arguments_preview? }`, the digest taken over the §6 canonical form of the arguments (the arguments themselves MUST NOT be transmitted). A binding does not make the descriptor truthful — nothing at this layer can — it is a **commitment device** with three effects: the §10.6 receipt records the tool + digest so a mismatch is **provable after the fact** against the agent's own logs; an escalation carries the **real call** to the subject beside the agent's prose; and a §10.5 authorization may carry **`require_binding: true`** to refuse to relax anything for an unbound request. `require_binding` is enforced for **authority-EXPANDING effects only** (`autoproceed`, `bias_bold`) — a rule that makes the agent *more* deferential keeps applying regardless, or the gate would itself become a way to shed a guardrail by omitting a field; the direction is always authority-narrowing, matching `expires_at`. Omitting `action_binding` is valid and resolves exactly as before (defaults preserve every existing integration); a **structurally invalid** binding MUST be rejected with `request_malformed`, because a caller that believes it is bound while the resolver treats it as unbound is worse off than one that never tried. ## 1. Introduction

The Phaedo Protocol defines how a portable cognitive fingerprint is represented, encrypted, signed, transported, and consulted by AI sessions and agents.

The protocol is a wire and storage format plus a small set of consultation interfaces. It is not the algorithm that produces a fingerprint, and it is not the user interface that manages one. The protocol exists so that a fingerprint produced by the Phaedo reference implementation and a fingerprint produced by any conforming third party tool are interoperable. A consuming AI session, agent, or injection adapter that conforms to this protocol can read either one without modification.

> **Direction (2026-06-09): consultation-led.** The protocol defines two consumption
> surfaces — **Injection** (Section 9, *push*: a projection inserted at session start so
> an assistant responds in the subject's voice) and **Consultation** (Section 10, *pull*:
> an agent queries *how the subject would decide* at a fork and gets a constrained signal,
> never content). As of this revision the project's center of gravity is **consultation**:
> injection has become commoditized (mainstream assistants ship auto-memory), while a
> portable, user-owned **decision-style oracle** an agent consults — bounded by §10.4 and
> backed by subject-authored standing policies (§10.5) — is the distinguishing primitive.
> This is a shift of *emphasis*, not of normative content: Sections 4–9 are unchanged and
> injection remains a fully supported conforming surface. The hero layers for consultation
> are **Decision and Risk** (§4.2.7) and **Big Picture** (§4.2.8). Rationale and the
> brief↔spec mapping: `docs/roadmap/consultation-reframe-2026-06-09.md`.

This document is v0.1, an internal working draft maintained alongside the Phase 0 prototype build. The first public release is v1.0, targeted for Phase 2. Between v0.1 and v1.0 the schema and envelope formats may change in incompatible ways. After v1.0, semantic versioning applies and any breaking change requires a major version bump.

Machine-readable **JSON Schemas** for the fingerprint (Section 4), the user configuration (Section 5), and the consultation surfaces (request 10.2, response 10.3, policy 10.5) are published alongside this document in `spec/schemas/` and are the normative machine form; the JSON examples in this prose are illustrative (see Section 6 for the canonical form).

### 1.1 Goals

1. **Portability.** Artifacts produced on one device (fingerprint and user configuration) are consumable by any conforming session or agent on any platform, given the user's consent and key material.
2. **User control.** Ciphertext is the only form of any artifact that ever leaves the user's vault device. Phaedo (the company) and any third party intermediary hold ciphertext only.
3. **Interoperability.** Any conforming producer or consumer can be substituted without coordination.
4. **Verifiability.** Integrity and authenticity are checkable at every boundary an artifact crosses.
5. **Forward compatibility.** Schema versioning, optional fields, and graceful degradation rules let v0.x consumers handle v0.y producers (and vice versa) within the same major version.

### 1.2 Out of Scope (v0.1)

- The persona signal extraction algorithm (proprietary; produces fingerprint content but is not described by the protocol).
- The Stained Glass obfuscation algorithm (proprietary; the protocol describes only the interface flag and the obfuscated payload envelope, not the obfuscation method itself).
- Enterprise admin tooling, fingerprint sync service APIs, billing protocols.
- The persona benchmark suite.
- The cryptographic format for cross device handoff (e.g., QR code export). v0.1 specifies the integrity envelope; the transport encoding is informative, not normative.

### 1.3 Document Conventions

Keywords MUST, MUST NOT, SHOULD, SHOULD NOT, MAY, and OPTIONAL are used as defined in RFC 2119 and RFC 8174.

JSON examples in this document are presented for readability and are not canonical. Section 6 specifies the canonical form used for signing and integrity checks.

Field names use `snake_case`. Identifiers, version strings, and algorithm identifiers are case sensitive.

### 1.4 Name, Governance, and Conformance Mark

**Name.** This standard is **Anamnesis** — a portable, vendor-neutral format for a subject's cognitive fingerprint and the interfaces that consume it. The name is Plato's term for knowledge as *recollection* (the *Meno*): the soul carries latent knowledge and re-surfaces it — which is exactly what a portable persona does across sessions. *Phaedo* is the reference implementation and the standard's initial steward, not the owner of the format ("Phaedo is the first and best implementation of Anamnesis"). "Phaedo Protocol" is retained as an **alias during v0.x** so existing references and the `phaedo_*` wire identifiers keep working; it is not a second standard.

**Wire identifiers.** v0.x retains the established `phaedo_*` field names and the `phaedo://` resource scheme as the normative identifiers (renaming them now would churn every existing artifact for no functional gain). Neutral `anam_*` field names and an `anam://` scheme become normative at **v1.0**, which is already the declared breaking-change boundary (§1, Introduction). v0.x → v1.0 producers/consumers SHOULD accept both as aliases across that cutover.

**Governance.** The standard is published openly (Apache-2.0 for the schemas/reference code, CC-BY for the prose) with a public, numbered RFC process (`docs/protocol/proposals/`). The intended home is a **neutral repository under a single steward** (Phaedo) — open and separable, without the overhead of a foundation; a multi-stakeholder steering model is adopted only once a second independent implementer exists. The open/proprietary boundary is fixed in Appendix A and does not move after v1.0.

**Conformance mark.** Authority over the standard rests in the **conformance program**, not the name — the USB-IF model (nobody owns USB; the conformance program shapes it). An **"Anamnesis Compatible"** certification mark MAY be granted to any implementation that passes the published conformance suite for its claimed level (§11): the §12 test vectors (`spec/test-vectors.mjs`), `phaedo-validate` clean for any fingerprints it emits (`spec/validate-fingerprint.mjs`), and a published §11.3 conformance statement. The mark is claimed per level — e.g. "Anamnesis Level 0 Compatible" (consumes a projection) through "Anamnesis Level 2 Compatible" (full producer) — so a chat client and a vault app advertise honest, differentiated conformance. The mark and its grant criteria are the durable control point; the schema is not.

## 2. Terminology

**Artifact.** A protocol level data object belonging to a subject. v0.1 defines two artifact kinds: the fingerprint (Section 4) and the user configuration (Section 5). All artifacts share the canonical serialization, encryption envelope, and integrity machinery (Sections 6 through 8).

**Fingerprint.** A structured, layered representation of a subject's cognitive patterns, sufficient for an AI session to align outputs with the subject's voice, expertise, decision style, and context. The fingerprint is not a transcript and is not a memory of conversations. It is a model derived from observation.

**User Configuration.** A subject authored artifact paired with a fingerprint. Carries standing instructions and an example corpus. Authored content rather than inferred patterns. See Section 5.

**Subject.** The natural person whose patterns and authored content are represented in the artifacts. The subject controls the keys.

**Layer.** A named partition of the fingerprint. Each layer covers a distinct dimension (domain, temporal, decision, etc.). Layers are independently selectable for injection and independently encryptable.

**Envelope.** The encrypted container holding the canonical bytes of an artifact, plus integrity and metadata fields. The same envelope format is used for both fingerprint and user configuration.

**Vault Device.** The device that holds the user's master key material in a secure element or trusted execution environment. In the Phaedo reference implementation, the vault device is a phone.

**Working Device.** The device on which the user runs an AI session that consumes an injection. Often a laptop. The working device receives a session scoped derived key, never the master key.

**Injection Adapter.** Software that inserts artifact projections (selected fingerprint layers, standing instructions, retrieved examples) into an AI session as system prompt or context. Plaintext artifact material exists only for the lifetime of an injection; a paired working-device client MAY additionally keep an at-rest cache of derived artifact material, but only as ciphertext (§7.4).

**Consulting Agent.** An autonomous agent that queries the fingerprint at decision points before taking consequential actions on the subject's behalf.

**Producer.** Any conforming software that creates or updates an artifact. A producer may produce one or both artifact kinds; conformance profiles distinguish Fingerprint Producer from Configuration Producer (Section 11.1).

**Consumer.** Any conforming software that reads an artifact, including injection adapters and consulting agents.

**Conformance Profile.** A named subset of the protocol that an implementation claims to support. See Section 11.

## 3. Architecture Overview

The protocol is layered:

```
+--------------------------------------------------------------------+
|  Application: AI session, agent, injection adapter                 |
+--------------------------------------------------------------------+
|  Consultation API (Section 10)   Injection API (Section 9)         |
+--------------------------------------------------------------------+
|  Fingerprint (Section 4)         User Configuration (Section 5)    |
+--------------------------------------------------------------------+
|  Canonical serialization (Section 6)                               |
+--------------------------------------------------------------------+
|  Encryption envelope (Section 7)                                   |
+--------------------------------------------------------------------+
|  Integrity and signing (Section 8)                                 |
+--------------------------------------------------------------------+
|  Transport binding (MCP, stdio, REST, ...) — see binding specs     |
+--------------------------------------------------------------------+
```

The core protocol is transport-agnostic: Sections 9 and 10 define message shapes, not how messages travel. How those shapes are carried over a concrete transport is specified in separate **binding** documents. The MCP binding — the path by which MCP-capable AI clients and agent frameworks reach Phaedo, and the primary transport for desktop and agent integration — is specified in `mcp-binding.md`.

The protocol carries two data artifacts: the fingerprint (an inferred behavioral model) and the user configuration (authored content). Both belong to the same subject, share the same envelope and integrity machinery, and are injected together at session start.

A typical flow:

1. Producer observes subject behavior on the working device. Raw observation is processed locally and discarded. A fingerprint delta is produced.
2. The delta is encrypted under the subject's key and merged into the canonical fingerprint on the vault device.
3. The user authors standing instructions and curates an example corpus through the configuration surface. The user configuration is encrypted under the same key material.
4. At session time, the user's session on the working device requests an injection. The injection adapter retrieves the encrypted fingerprint and the encrypted user configuration, decrypts them within a session scoped boundary, selects relevant layers and instructions, and inserts a combined projection into the AI session.
5. After the session, the projection is destroyed. Only the encrypted fingerprint and configuration persist.
6. For agent consultation, the consulting agent issues a query through the consultation API. The fingerprint answers in a constrained shape (Section 10). The agent does not receive the full fingerprint or configuration.

## 4. Fingerprint Schema

### 4.1 Top Level Document

The canonical fingerprint document is a single JSON object:

```json
{
  "phaedo_protocol_version": "0.1",
  "fingerprint_id": "f1b9c4e2-7d3a-4e8b-9c0f-2a1b3c4d5e6f",
  "subject_id": "opaque_subject_identifier",
  "created_at": "2026-04-28T17:00:00Z",
  "updated_at": "2026-04-28T17:00:00Z",
  "persona_strength": 0.62,
  "schema_revision": 1,
  "layers": {
    "surface": { ... },
    "behavioral": { ... },
    "creative": { ... },
    "domain_and_expertise": { ... },
    "temporal_and_context": { ... },
    "collaboration_and_relationship": { ... },
    "decision_and_risk": { ... },
    "big_picture": { ... }
  },
  "extensions": {}
}
```

Field definitions:

| Field | Type | Required | Description |
|---|---|---|---|
| `phaedo_protocol_version` | string | yes | Protocol version this document conforms to. Format: `MAJOR.MINOR`. |
| `fingerprint_id` | string (UUID v4) | yes | Stable identifier for this fingerprint instance. |
| `subject_id` | string | yes | Opaque identifier for the subject. MUST NOT be a personally identifying value. |
| `created_at` | string (RFC 3339) | yes | UTC timestamp of fingerprint creation. |
| `updated_at` | string (RFC 3339) | yes | UTC timestamp of most recent layer update. |
| `persona_strength` | number | yes | Scalar in `[0.0, 1.0]`. Producer's confidence that the fingerprint is a useful match. |
| `schema_revision` | integer | yes | Integer revision counter. Incremented on any layer schema change within the same protocol version. |
| `layers` | object | yes | Map of layer name to layer document. See Section 4.2. |
| `consult_policies` | object | no | Optional consultation deference policies (Section 10.5) carried with the fingerprint so they travel across every transport. See `spec/schemas/consultation-policy.schema.json`. |
| `extensions` | object | no | Reserved for producer specific or experimental fields. Consumers MUST ignore unknown extension keys. |

### 4.2 Layers

The fingerprint is partitioned into eight named layers. Each layer is a JSON object. A producer MAY omit any layer. A consumer MUST tolerate any combination of present and absent layers.

Each layer document conforms to a common envelope:

```json
{
  "layer_version": "0.1",
  "last_updated": "2026-04-28T17:00:00Z",
  "confidence": 0.0,
  "signals": [],
  "summary": ""
}
```

| Field | Type | Required | Description |
|---|---|---|---|
| `layer_version` | string | yes | Layer schema version, independent of top level protocol version. |
| `last_updated` | string (RFC 3339) | yes | Most recent observation that updated this layer. |
| `confidence` | number | yes | Scalar in `[0.0, 1.0]`. Producer's confidence in this layer specifically. |
| `signals` | array | yes | List of structured signal objects. Schema per layer. |
| `summary` | string | yes | Short natural language summary of the layer for injection. v0.1 limit: 2000 characters. |

The eight layers are presented in canonical ordering. This is the order producers SHOULD use when serializing the `layers` object and the order consumers SHOULD use when constructing a default projection.

#### 4.2.1 Surface

Communication style, tone, formality, vocabulary, format preferences.

Example signals: preferred sentence length distribution, em dash avoidance, hedge frequency, emoji usage, salutation style, formatting tendencies (bullets vs prose, headers vs flat).

#### 4.2.2 Behavioral

How the subject works the material. Iteration patterns, editing behavior, what the subject accepts and rejects in AI output, where polish stops. The "how you work" signals, distinct from the "how you decide" signals in Decision and Risk (Section 4.2.7).

Example signals: accept rate on AI suggestions by category (technical, narrative, structural), edit depth distribution, drafts before declaring done, where the subject corrects vs leaves rough, preference for outline first vs draft first, frequency of self correction.

#### 4.2.3 Creative

Aesthetic sensibilities, mental models, how the subject reasons by analogy.

Example signals: analogy density, preferred metaphor domains, aesthetic stop conditions, recurring framing instincts, what counts as elegant or worth shipping.

#### 4.2.4 Domain and Expertise

Areas of deep knowledge, specialized vocabulary, expected depth and technical complexity of responses.

Example signals: technical vocabularies fluent in, citation patterns, depth of follow up questions in a given domain, comfort with jargon, meta knowledge about own expertise gaps.

#### 4.2.5 Temporal and Context

How needs and thinking shift based on project phase, urgency, and working mode.

Example signals: short term tactical vs long term strategic balance, recurring constraints by phase, deadline pressure response, context switching rate, active project context.

#### 4.2.6 Collaboration and Relationship

How the subject communicates with different audiences, formality shifts, and relationship context.

Example signals: directness gradient by audience (reports vs peers vs leadership vs vendors), information density, escalation patterns, trust calibration patterns.

#### 4.2.7 Decision and Risk

How the subject commits to positions and actions. Evidence thresholds, risk tolerance per domain, reversibility preferences, response to options versus direct recommendations. The "how you decide" signals, distinct from the "how you work" signals in Behavioral (Section 4.2.2).

Example signals: evidence thresholds before committing by domain, reversibility preferences, default escalation behavior, comfort with one way doors vs reversible moves, preference for option sets vs single recommendations, posture under ambiguity (delay, ask, default).

The per-signal shape for this layer is **normatively specified** (resolving open question 13 for the Decision and Risk layer first — see `spec/schemas/decision-risk-signal.schema.json`): each signal carries `dimension`, `polarity`, `value`, `confidence`, and `evidence_basis` (`observed` | `corroborated` | `self_reported`). A consumer SHOULD weigh signals by `confidence` and trust `observed`/`corroborated` above `self_reported`. The OPTIONAL `domain` field scopes a signal to a domain (same substring namespace as `action_descriptor.domain`, Section 10.2): the reference producer emits it as a **prototype** — a session's Decision and Risk signals are tagged only when one domain clearly dominates the subject's own messages, ambiguous sessions stay untagged — and a consumer prefers a matching-domain signal, falls back to an untagged one, and MUST NOT borrow a signal tagged for a different domain. Untagged signals keep fingerprint-wide semantics, so existing fingerprints are unaffected. `threshold` remains reserved (not yet emitted). The other seven layers' signal shapes remain implementation-defined in v0.1.

#### 4.2.8 Big Picture

How the subject sees themselves as a thinker and collaborator. Surfaces what the structured layers miss.

Example signals: recurring strategic frames, stable principles, self description that holds across contexts, multi year goal coherence, narrative the subject uses to explain their own work.

### 4.3 Signal Polarity

Signals within any layer carry one of two polarities:

- **Positive (preference).** Patterns the subject exhibits or values that align with the subject's working style.
- **Negative (anti-preference).** Patterns the subject avoids, rejects, or stops on. Producers SHOULD record these explicitly rather than relying on the absence of a positive signal.

Anti-preferences are diagnostic. Most subjects can articulate what they reject in AI output faster and more confidently than what they prefer. The extraction algorithm and any user facing intake (interview, settings, onboarding) SHOULD prompt for both polarities. Negative space is as load bearing as positive space.

Signal polarity is recorded in the per-signal schema, which is **normative for all layers** as of v0.1.17 (`fingerprint.schema.json#/$defs/signal`, generalizing the §4.2.7 Decision & Risk specialization; open question 13 resolved). When constructing an injection projection, consumers MUST honor anti-preference signals. If a layer summary or positive signal in a layer contradicts an anti-preference signal in the same layer, the anti-preference takes precedence.

Anti-preferences MAY also be authored explicitly by the subject through the user configuration (Section 5). When the same anti-preference appears in both the fingerprint (inferred) and the user configuration (authored), they reinforce each other; consumers SHOULD treat the authored form as canonical for the purpose of resolving conflicts.

### 4.4 Persona Strength

`persona_strength` at the document level is a producer computed scalar. The protocol does not specify how it is computed (the algorithm is proprietary). Consumers MAY use it to gate features (for example, an injection adapter MAY refuse to inject a fingerprint with strength below a configured threshold).

### 4.5 Extensions

The `extensions` field is reserved for producer specific or experimental data that does not yet have a standard home. Producers SHOULD prefix extension keys with a producer identifier (for example, `phaedo_io.x_experimental_dream_journal`). Consumers MUST ignore unknown extension keys.

Extensions are not part of the canonical document for signing purposes. See Section 6.

### 4.6 Layer Admission

All eight layers (Section 4.2) are **behavioral / persona** layers: each admits structured signals describing *stable patterns* in how the subject communicates, works, decides, and thinks. They MUST NOT carry **episodic content** — facts about the subject's life, environment, or specific entities (names, URLs, email addresses, domains, account identifiers, dates of specific events). Episodic facts are a separate, opt-in **content scope** outside this specification; a fingerprint is a model derived from observation, not a memory of conversations (Section 2).

This boundary is the protocol's privacy and differentiation property: a fingerprint that leaks episodic facts into its behavioral layers has rebuilt content memory with extra steps. Producers MUST NOT emit a signal whose `value` is an episodic fact; consumers and validators SHOULD reject one. A **conformant fingerprint** carries no URL, email address, or specific domain in any signal value. The reference producer enforces this (it drops such values from the projection — `extraction/fingerprint-update.js`) and the reference validator flags them as errors (`spec/validate-fingerprint.mjs`, high-precision URL/email/domain markers).

The per-layer **signal field vocabulary** — which `field` values each layer canonically carries — is published as a normative reference in `spec/layer-vocabulary.json` (generated from, and kept in sync with, the reference producer's catalog). An unknown `field` is not itself a conformance failure (the vocabulary evolves), but episodic *content* in any value is.

### 4.7 Conflict Resolution

A layer's `signals[]` is an **evidence log**: it MAY hold several signals for the same `field` with different `value`s, learned from different sources at different times. The array is therefore the provenance record — retained in full. But a consumer needs **one resolved value per dimension** to act on, and a projection (Section 9) that asserts two conflicting values for one dimension with no resolution is a defect — most dangerously for decision-relevant dimensions an agent consults before acting (e.g. autonomy). This section defines the **deterministic** resolution so every conformant implementation computes the same resolved value from the same evidence log. (User-*authored* configuration — Section 5 / Section 5.2 `standing_rules` / Section 10.5 — overrides any inferred resolution; this section governs inferred signals only. A `standing_rules` instruction carrying a `decision` binding for a dimension makes that dimension authored-canonical for the projection, ahead of any inferred resolution computed here.)

**Polarity precedence (Section 4.3) is applied first**: within a field, a negative (anti-preference) signal is the effective one over a positive. Value resolution then runs over the effective set.

**Evidence-tier precedence with a minimum-evidence floor.** Rank candidate signals by `evidence_basis`: `corroborated` > `observed` > `self_reported` (an absent/unknown basis ranks lowest). Within a tier, higher `observation_count` wins, then more recent `last_observed`, then a stable order on the value (full determinism — no ties). The **resolved value** is the top-ranked candidate, with one safeguard:

> **Minimum-evidence floor.** An `observed`/`corroborated` signal **overrides** a contradicting `self_reported` (interview) value only once it has accumulated `observation_count ≥ RESOLUTION_FLOOR` (normative default **3**). Below the floor, a genuine conflict between inferred and self-reported values resolves to **`status: "unresolved"`** rather than confidently flipping. A consumer MUST treat an `unresolved` dimension conservatively — for a consultation (Section 10) this means biasing toward `clarify`/`escalate`, never reading it as a confident instruction.

The floor exists because the most dangerous failure is *thin* observed evidence overriding a stated preference: two stray observations should not flip "check before acting" into "execute without dialogue" for an autonomous agent. Agreement across sources (same value) is never a conflict and always resolves.

**Output.** Resolution yields, per dimension: the resolved `value`, its `evidence_basis` and `confidence`, a `status` of `resolved` or `unresolved`, and a `provenance` array of all candidate signals. Provenance requires no new wire structure — it *is* the `signals[]` log. The reference algorithm is `resolveDimension()` / `resolveLayer()` in `spec/validate-fingerprint.mjs`; test vectors are `spec/test-vectors/resolution.json` (category TC-RESOLVE). See Proposal 0006.

**Effective resolution in context (v0.1.43, resolves OQ7).** The paragraph above governs *inferred* signals; the parenthetical "authored overrides inferred" is now exact, at dimension granularity, in an optional **domain context** — the rules for a standing instruction that contradicts a high-confidence fingerprint signal *in only one domain*. Per dimension, the **specificity ladder** (a lower tier is consulted only when every higher tier is empty):

1. **`authored_domain`** — a Section 5.2 instruction with a `decision` binding for this dimension whose `decision.domain` matches the context domain (resolver substring namespace: the context domain string *contains* the rule's domain, case-insensitively). A domain-bound rule NEVER governs outside its domain: with a non-matching or unknown context it is skipped entirely, so an inferred signal keeps governing everywhere else.
2. **`authored_global`** — a bound instruction with no `decision.domain`. Authored beats inferred regardless of the signal's confidence or evidence tier.
3. **`inferred_domain`** — Section 4.2.7 domain-tagged signals matching the context domain, resolved among themselves by the rules above. An `unresolved` at this tier does NOT fall through to tier 4: a contested domain-specific dimension stays contested (assert nothing).
4. **`inferred_global`** — untagged signals. When a context domain is known, signals tagged with a *different* domain are excluded (they describe another context); with no context domain, all signals resolve together (the pre-v0.1.43 behavior, unchanged).

Within an authored tier, ties break by lowest `priority`, then `created_at`, then `instruction_id` — fully deterministic. An authored resolution carries the rule's `decision.value` when present (template-sourced precise value) or `value: null` with the rule's `polarity` (a valueless negative binding is a cautious bias, which Section 10 consumers already map to `bias_cautious`). The reference algorithm is `resolveEffective()` in `extraction/resolve.js` (re-exported by `spec/validate-fingerprint.mjs`); test vectors are the `R-EFFECTIVE-*` entries in `spec/test-vectors/resolution.json` (category TC-RESOLVE).

> **Conflict records (optional staging surface).** A producer MAY make an `unresolved` contradiction *durable and reviewable* by staging it in an optional `phaedo_fingerprint.conflict_records[]` queue when it detects, at reconcile time, a new `observed` value contradicting a `self_reported` one below the floor. A record is `{ conflict_id, layer, field, domain?, status: "open" | "resolved" | "dismissed", detected_at, last_seen, resolved_at?, candidates[] }`, where `candidates[]` is the both-sides provenance. Like `suggested_rules[]` (§5.2 note), this is a producer-written **proposal queue**: never injected, never consulted, derived from the evidence log (no wire change; `phaedo_protocol_version` stays `0.1`). It auto-closes (`resolved`) once the inferred side crosses the floor; a subject's `dismissed` is sticky. It exists so an autonomous agent's most decision-relevant contradictions are auditable and reviewable rather than silently collapsed by an upstream confidence merge. **Injection suppression (normative for the reference producer):** while a conflict is `open`, the producer **withholds that dimension from the projection** (Section 9) — the reference producer's `renderLayerSummary` omits an open-conflict `(field[, domain])` — so a contested value is **not asserted** to a consuming agent until the subject settles it (settling authors a canonical rule; dismissing un-suppresses to the confidence-merged value). Reference: `detectConflicts()` / `reconcileFingerprint()` / `renderLayerSummary()` in `extraction/`, locked by `scripts/test_conflict_records.mjs`. **Consult suppression (the symmetric half, §10):** the reference resolver likewise **withholds an open-conflict dimension from the consultation cue readers** — a contested cue is treated as no coverage, so a consult whose every relevant dimension is contested returns `insufficient_signal` (abstain → escalate to the subject) rather than a confident answer on an unsettled dimension. The model-judge path inherits this by reasoning over the already-suppressed projection. Reference: `mcp/consult-core.js` (`openConflictKeys` / `isFieldContested`), locked by `mcp/test-consult.mjs`.

## 5. User Configuration

The user configuration is a sibling artifact to the fingerprint. It carries information the subject authors directly rather than information inferred from observation.

The fingerprint is a behavioral model. The user configuration is authored content. Both belong to the same subject, both are encrypted under the same key material, both ride the same envelope, and both are injected at session start. The protocol treats them as separate artifacts so that authored content is not reverse engineered from behavior, and so that inferred patterns do not have to share a structure with explicit rules.

Authored content has different properties than inferred content:

- It does not get learned over time. It is stated once and edited when needed.
- It does not have a producer assigned confidence score.
- It does not improve with more observations.
- It is applied verbatim, not summarized.

Treating it as a layer of the fingerprint creates category confusion. Treating it as a sibling keeps each artifact's semantics clean.

### 5.1 Top Level Document

```json
{
  "phaedo_protocol_version": "0.1",
```

### 5.2 Standing Instructions

A standing instruction is an explicit rule the subject would state to every AI session if they remembered. Standing instructions are the highest leverage user configuration content because they are direct, authored, and applied verbatim.

> **v0.1 A-home — `standing_rules` (Proposal 0007) — migration in flight (v0.1.41).** The §5 User Configuration artifact is the destination home. For v0.1, standing instructions are carried on the fingerprint as `phaedo_fingerprint.standing_rules` (the same pragmatic A-home §10.5 policies use), so they travel and inject today with no new artifact. A `standing_rules` entry is this §5.2 object plus a `kind` discriminator (`instruction` | `authorization`, per Proposal 0003) and an optional `decision` binding to a Decision & Risk dimension (`{dimension, polarity, domain}`); a bound rule is authored-canonical for that dimension (§4.7). **Parts 1 + 2 of the migration have landed:** the §5 artifact schema is published (`spec/schemas/user-configuration.schema.json`) with the entry shape canonical THERE (`$defs/standing_instruction`) — the A-home `standing_rules[]` `$ref`s it, so the homes cannot drift (part 1, v0.1.41); and the sibling now **persists in the vault payload** (`phaedo_user_configuration`, Appendix C), maintained by the reference SW's write finalizer (`user-config.js maintainUserConfiguration`) on every vault write, with **reads §5-canonical** — `renderContextBlock` and the §10 policy loader consume the sibling's `standing_instructions` instead of the A-home when present (part 2, v0.1.45). Dual-home rule: the §5 document is canonical when present; the A-home remains the *transported* form until part 3 (cross-device `artifact_kind:'user_configuration'` envelope transport + mobile parity), after which the A-home retires with `consult_policies` (the v0.2.0 breaking line). Authored-only is structural: the reference extraction pipeline has no write-path into `standing_rules` (locked by `scripts/test_standing_rules_invariant.mjs`), and the derivation seam never migrates `suggested_rules` (a proposal queue is not authored content).

> **Delta promotion (the steady-state seed).** Onboarding (the `rule_elicitation` flow) seeds the layer at cold start; after that, the producer MAY *propose* rules without ever authoring them. When an inferred Decision & Risk signal becomes established (observed/corroborated, `observation_count ≥ 3`, no rule yet on that dimension), it is staged as a `suggested` candidate in `phaedo_fingerprint.suggested_rules[]` — a proposal queue, **not** authored content, never injected or consulted. The subject reviews and **endorses** (writing a `standing_rules` entry with `source:"delta_promotion"`) or rejects (kept `dismissed`, not re-proposed). Endorsement is the only write into the authored array, so authored-only holds through the loop. Reference: `extraction/rule-promotion.js` (stage) + `rule-review.js` (endorse/reject).

Examples (illustrative, not normative):

- "Use prose by default. Do not use bullet lists unless I ask."
- "Always show me failure modes alongside happy paths."
- "Default to skeptical pushback on my own ideas before agreeing."
- "Refer to me as Randy."
- "Do not use the word leverage as a verb."

Each instruction is an object:

```json
{
  "instruction_id": "i1a2b3c4-d5e6-7f89-0a1b-2c3d4e5f6789",
  "text": "Use prose by default. Do not use bullet lists unless I ask.",
  "scope": "global",
  "priority": 100,
  "created_at": "2026-04-28T17:00:00Z",
  "updated_at": "2026-04-28T17:00:00Z"
}
```

| Field | Type | Required | Description |
|---|---|---|---|
| `instruction_id` | string (UUID v4) | yes | Stable identifier. |
| `text` | string | yes | The rule statement. UTF-8, NFC normalized. v0.1 limit: 1000 characters. |
| `scope` | string | yes | One of `global`, `domain`, `task`. `global` (or absent) = always active. `domain` and `task` are normative as of v0.1.42 (OQ5) — see the activation rules below. |
| `scope_domains` | array of strings | when `scope` = `domain` | The domains this instruction activates for. Same case-insensitive substring namespace as `action_descriptor.domain` / `match.domains` / `session_context.domain`: active when the session's domain string *contains* one of these entries. |
| `scope_tasks` | array of strings | when `scope` = `task` | Task descriptors this instruction activates for, matched case-insensitively as substrings of the session's `task_hint` (Section 9.2). |
| `priority` | integer | yes | Ordering hint. Lower values inject first. Ties broken by `created_at`. |
| `created_at` | string (RFC 3339) | yes | UTC timestamp. |
| `updated_at` | string (RFC 3339) | yes | UTC timestamp. |

Standing instructions are injected verbatim. Producers MUST NOT summarize, paraphrase, or interpret them. Consumers MAY omit instructions that exceed the session's token budget but MUST omit them in priority order, dropping highest priority value (lowest precedence) first.

**Scope activation (v0.1.42, resolves OQ5).** A `domain`- or `task`-scoped instruction activates based on session context, with two consumption modes:

1. **Deterministic consumers** (the Section 10 consultation surfaces, layer selection, any consumer that evaluates rules programmatically): a scoped instruction is active **iff** the session context positively matches — for `domain`, the session's domain string (`session_context.domain`, or a consultation's `action_descriptor.domain`) case-insensitively *contains* one of `scope_domains`; for `task`, the session's `task_hint` case-insensitively *contains* one of `scope_tasks`. An unknown or missing context is a non-match: the rule is **inactive (fail-closed)**. A consumer that cannot establish the session's domain or task MUST NOT apply a scoped rule globally.
2. **Model-mediated injection consumers** (a Section 9 projection assembled *before* the session's subject matter is knowable, e.g. a chat-surface injection at session start): the consumer MAY include a scoped instruction rendered with an **explicit conditional scope prefix** (the reference renders "Only when the session involves *X*: …"), delegating activation to the consuming model. A consumer that CAN evaluate the scope (its injection request carried `session_context.domain` / `task_hint`) SHOULD filter deterministically per mode 1 instead — a matched rule renders plain (the condition already held), an unmatched rule is omitted.

The two modes never mix per rule evaluation: a rule whose scope was evaluated deterministically is either plain-rendered or omitted; the conditional prefix appears only when the consumer could not evaluate that rule's scope dimension. Scope activation composes with, and does not replace, the finer-grained v0.1 mechanisms (`decision.domain` on a bound instruction; `match.domains` on an authorization) — those continue to gate the consultation resolver directly. Reference: `user-config.js instructionActiveFor` (deterministic contract) + `context-block.js renderOperatingRules` (injection renderer, both modes); locked by `scripts/test_user_config.mjs` (incl. a cross-implementation parity matrix) and `scripts/test_context_block.mjs`.

### 5.3 Example Corpus

The example corpus is a small set of representative outputs the subject has marked as exemplary. The corpus answers "what does good look like for me" through samples rather than rules.

Each example is an object:

```json
{
  "example_id": "e2b3c4d5-e6f7-89a0-b1c2-d3e4f5a6b7c8",
  "kind": "writing_sample",
  "label": "Investor update, calm tone",
  "content": "<the sample content>",
  "tags": ["voice", "investor"],
  "created_at": "2026-04-28T17:00:00Z"
}
```

| Field | Type | Required | Description |
|---|---|---|---|
| `example_id` | string (UUID v4) | yes | Stable identifier. |
| `kind` | string | yes | One of `writing_sample`, `decision_record`, `code_sample`, `other`. |
| `label` | string | yes | Short description for indexing and display. |
| `content` | string | yes | The sample. UTF-8. v0.1 limit: 8000 characters per example. |
| `tags` | array of strings | no | Producer or user assigned tags for retrieval. |
| `created_at` | string (RFC 3339) | yes | UTC timestamp. |

v0.1 specifies a soft cap of 20 examples per corpus and 8000 characters per example. Consumers SHOULD treat the corpus as a retrieval source rather than a verbatim dump: select the most relevant examples for a given session against session context (Section 9.2) rather than injecting all of them.

### 5.4 Pairing with the Fingerprint

A user configuration is paired with exactly one fingerprint via `fingerprint_id`. A fingerprint MAY exist without a paired configuration (a subject who has not authored any standing instructions or examples). A configuration without a paired fingerprint is invalid in v0.1.

When both are present, consumers SHOULD inject both at session start. The injection adapter assembles a combined projection containing:

1. Standing instructions, in priority order.
2. Selected layer projections from the fingerprint (Section 9.4).
3. Selected examples from the corpus, retrieved against session context.

Order matters. Standing instructions appear before fingerprint material in the assembled projection. They are explicit rules and SHOULD take precedence when authored configuration conflicts with inferred patterns.

### 5.5 Encryption and Integrity

The user configuration uses the same envelope (Section 7), canonical serialization (Section 6), and integrity scheme (Section 8) as the fingerprint. The same master key material MAY be used, with a distinct domain separation context (`phaedo:config:enc:v0.1`) to derive the configuration encryption key. This keeps fingerprint and configuration ciphertexts independent under the same root key, so a leak of one does not compromise the other.

### 5.6 Authoring Surface

The protocol does not specify a user authoring surface. Producers MAY expose any interface (text editor, structured form, voice capture, prompt rewriter). v0.1 places one constraint on producers: standing instructions and examples MUST be confirmed by the subject before being committed to the configuration. Inferred edits are forbidden. Configuration is authored content by definition.

### 5.7 Commitments (decision state)

The eight fingerprint layers are **dispositional**: they model how a subject decides — response length, tone, iteration style, ambiguity posture, evidence threshold. Even `temporal_and_context` carries traits (early-project mode, urgency baseline, working mode) rather than situation. Section 4.6 forbids episodic content in behavioral layers precisely so that a behavioral model never becomes a dossier.

That leaves a gap an agent acting on a subject's behalf falls directly into. A consultation can return "this subject would be cautious here" when the correct answer is "this subject has already decided this" — they already declined that vendor, they are on leave until the fourth, that budget is frozen, that negotiation is live. **Style without state is how a proxy contradicts the person it represents.**

Commitments close that gap and nothing wider. They are **not memory**: no recall, no retrieval, no conversation history. They are a short, authored, always-expiring list of facts that should change a *decision*.

```json
{
  "commitment_id": "8c1f2e7a-4b6d-4f19-a2c3-9e5d7b1a0c4f",
  "kind": "commitment",
  "statement": "I already told ACME we are not renewing.",
  "domains": ["procurement"],
  "effect": "escalate",
  "disclose": false,
  "expires_at": "2026-09-01T00:00:00Z",
  "source": "subject"
}
```

Machine form: `spec/schemas/commitments.schema.json`. Normative rules:

- **Authored only.** A producer MUST NOT infer a commitment. `source` is an enum whose only member is `subject`, so an inferred value is a schema violation rather than a convention. Subject confirmation before commit is required, as for all §5 content (§5.6).
- **Deferential only.** `effect` is restricted to `escalate`, `decline`, `bias_cautious`. `autoproceed` is not expressible: being bound by something is never a reason to grant an agent more latitude, and autonomy expansion has exactly one path (a §10.5 authorization, §10.7). This keeps commitments from becoming a second, unaudited route to autonomy.
- **Perishable.** `expires_at` is REQUIRED. Decision state that outlives its situation silently blocks work forever, which is worse than not recording it. A lapsed commitment MUST be ignored, enforced exactly as a §10.5 authorization's expiry is.
- **Never injected.** Commitments MUST NOT appear in the §9 projection. Their text is episodic by nature — it names counterparties, dates and amounts — so it is consumed only at the §10 consultation boundary. The §4.6 episodic rail therefore deliberately does **not** apply to a commitment's `statement`, the same carve-out §5.3 example content receives, and for the same reason: the content never reaches a model verbatim as part of a persona.
- **Disclosure is opt-in.** `disclose` defaults to `false`. When false, a resolver MUST NOT place the statement in the §10.3 `rationale_hint`; it returns a generic hint instead. An arbitrary agent learning *"the subject already told ACME no"* is a disclosure, not a rationale. The **decision** always crosses; the **reason** crosses only when the subject said it may.
- **Home.** v0.1 carries commitments on the fingerprint (`phaedo_fingerprint.commitments`), the same A-home `standing_rules` uses and for the same reason: they travel on every sync with no new transport. The §5 sibling home follows the same migration path.

A consumer applies commitments at the consultation boundary by evaluating them alongside §10.5 authorizations, matching `domains` in the same case-insensitive substring namespace. Because a commitment can only be deferential, ordering between the two sets cannot produce an unsafe result.

> **Not yet specified.** Standing budgets (OQ17) are the other form of decision state — a running counter decremented per resolved action. They belong in this artifact rather than in a behavioral layer; the shape is deferred to the release that implements them.

## 6. Canonical Serialization

For signing and integrity checks, an artifact document (fingerprint or user configuration) MUST be serialized in a canonical form so that producer and consumer compute identical bytes from identical content. The canonicalization rules in this section apply to every artifact kind.

> **Implementation status (updated v0.1.44, 2026-07-19).** The reference `Phaedo.Envelope.canonicalStringify` (extension `envelope.js`, byte-identical mobile `envelope.ts`) now implements the **full RFC 8785 method** — closing the v0.1.15 note's "JCS-compatible subset" gap ahead of §8.3 signing (still deferred to v1.0). In ECMAScript, `JSON.stringify` already emits RFC 8785-conformant scalars — shortest-round-trip ES number formatting (`1e+21`, `1e-7`, `-0` → `0`, trailing-zero drop) and minimal string escaping (short escapes, `\u00XX` only for remaining control characters) — so the full method = recursive UTF-16 code-unit key ordering **plus explicit rejection** of values JSON cannot express: non-finite numbers (NaN/Infinity) **throw** rather than silently corrupting canonical bytes as `null`, and a top-level `undefined` throws rather than emitting invalid output (inside containers, `undefined`/function/symbol follow `JSON.stringify` semantics: omitted from objects, `null` in arrays). Today this canonicalization is exercised on the **envelope metadata AAD binding** (§7.3) — the encrypted artifact *body* remains plain `JSON.stringify` (confidentiality + integrity come from the AES-GCM envelope, §7) until §8.3 signing consumes canonical artifact bytes, for which the method now stands ready per §6.1. Existing envelopes are unaffected: for every value shape v0.1 metadata actually carries, the full method is byte-identical to the prior subset. **Locked by conformance vectors** — `spec/test-vectors/canonicalization.json` (category TC-CANON, incl. ES number-formatting, escaping, unicode key-sort, and rejection cases), run by `spec/test-vectors.mjs`; cross-implementation parity by `scripts/test_cross_compat.mjs`.

### 6.1 Canonicalization Method

v0.1 specifies **JSON Canonicalization Scheme (RFC 8785)** as the canonicalization method.

Implementations MUST:

1. Build a JSON object containing all required top level fields of the artifact being serialized. For a fingerprint, this includes any present layer documents (Section 4.2). For a user configuration, this includes the standing instructions array and the example corpus array (Section 5).
2. Exclude the `extensions` field from the canonical form. Extensions are explicitly out of scope for signing in v0.1.
3. Apply RFC 8785 canonicalization to the resulting object.
4. Use the resulting byte sequence (UTF-8) as input to encryption and integrity operations.

### 6.2 String Encoding

All strings are UTF-8. Implementations MUST normalize text to NFC before canonicalization to avoid signature breakage from equivalent but byte different strings.

### 6.3 Numbers

Numeric fields are serialized per RFC 8785 number rules. Real number fields in `[0.0, 1.0]` (fingerprint `persona_strength`, per layer `confidence`) SHOULD be expressed with three decimal places of precision in canonical form. Integer fields (such as `schema_revision` and standing instruction `priority`) are serialized as exact integers.

## 7. Encryption Envelope

### 7.1 Algorithm

v0.1 specifies **AES-256-GCM** as the only normative encryption algorithm. Implementations MUST support it. Future versions may add algorithms; the algorithm identifier field exists to support that.

### 7.2 Envelope Structure

The envelope is a JSON object:

```json
{
  "phaedo_envelope_version": "0.1",
  "alg": "AES-256-GCM",
  "iv": "base64url(12 bytes)",
  "kdf": {
    "alg": "PBKDF2-HMAC-SHA-256",
    "salt": "base64url(16 bytes)",
    "iterations": 600000
  },
  "ciphertext": "base64url(...)",
  "tag": "base64url(16 bytes)",
  "metadata": {
    "artifact_kind": "fingerprint",
    "fingerprint_id": "f1b9c4e2-7d3a-4e8b-9c0f-2a1b3c4d5e6f",
    "created_at": "2026-04-28T17:00:00Z"
  }
}
```

For a user configuration envelope, `artifact_kind` is `user_configuration` and the metadata carries `configuration_id` and `fingerprint_id` (the paired fingerprint) instead of `fingerprint_id` alone:

```json
{
  "phaedo_envelope_version": "0.1",
  "alg": "AES-256-GCM",
  "iv": "...",
  "kdf": { "...": "..." },
  "ciphertext": "...",
  "tag": "...",
  "metadata": {
    "artifact_kind": "user_configuration",
    "configuration_id": "c2a8d4f1-9e6b-4c2a-8d4f-1e6b4c2a8d4f",
    "fingerprint_id": "f1b9c4e2-7d3a-4e8b-9c0f-2a1b3c4d5e6f",
    "created_at": "2026-04-28T17:00:00Z"
  }
}
```

Fields:

| Field | Required | Description |
|---|---|---|
| `phaedo_envelope_version` | yes | Envelope format version. |
| `alg` | yes | Algorithm identifier. v0.1 only `AES-256-GCM`. |
| `iv` | yes | 96 bit initialization vector, base64url encoded, no padding. MUST be unique per encryption with the same key. |
| `kdf` | conditional | Required when the encryption key is derived from a passphrase. Omitted when an externally managed key (such as a secure enclave wrapped key) is used. |
| `kdf.alg` | yes (when present) | KDF identifier. v0.1 only `PBKDF2-HMAC-SHA-256`. |
| `kdf.salt` | yes (when present) | 128 bit salt, base64url encoded. |
| `kdf.iterations` | yes (when present) | Iteration count. v0.1 minimum: 600,000. |
| `ciphertext` | yes | AES-256-GCM ciphertext over the canonical artifact bytes (Section 6). |
| `tag` | yes | 128 bit GCM authentication tag. |
| `metadata` | yes | Cleartext metadata for routing and indexing. Does NOT include any artifact content. |
| `metadata.artifact_kind` | yes | One of `fingerprint`, `user_configuration`. Identifies which artifact the envelope wraps without requiring decryption. |
| `metadata.fingerprint_id` | conditional | Required for `fingerprint` envelopes. Required for `user_configuration` envelopes (identifies the paired fingerprint). |
| `metadata.configuration_id` | conditional | Required for `user_configuration` envelopes. |
| `metadata.created_at` | yes | UTC timestamp of envelope creation. |

### 7.3 Authenticated Associated Data

The canonical serialization of the `metadata` field MUST be passed as additional authenticated data (AAD) to AES-GCM. This binds the cleartext metadata to the encrypted body so a tampered metadata field is detected on decrypt.

### 7.4 Key Material

v0.1 supports two key material sources for the **encryption envelope** (wire / portable export):

1. **Passphrase derived.** The user supplies a passphrase. The producer derives a 256 bit key with PBKDF2-HMAC-SHA-256. The KDF parameters are recorded in the envelope.
2. **Enclave wrapped.** The 256 bit key is generated and stored in a secure enclave or TEE on the vault device. The enclave returns a wrapped key for transport between vault and working device. v0.1 does not normalize the wrapping format; this is deferred to v0.2.

Separately, for the **working-device at-rest cache** (distinct from the envelope above):

3. **Working-device cache key (browser-held).** A paired client (e.g. the browser extension) MAY encrypt its at-rest fingerprint cache under a per-install, **non-extractable** AES-256-GCM key held by the client itself (reference implementation: a WebCrypto `CryptoKey` in IndexedDB, owned by the service worker). This is **defense-in-depth for the derived cache only** — it is NOT the master key (which never leaves the vault device), and because the client can decrypt without the vault device it provides neither phone-gated access nor forensic-grade protection. The cache is recoverable from the vault device on key loss (re-sync). See `docs/roadmap/extension-at-rest.md` for rationale and the (rejected) alternatives.

### 7.5 Lock Scope and Key Caching

v0.1 leaves lock scope and key caching policy to the implementation, with the following constraint: the working device MUST NOT retain plaintext key material in process memory for longer than the duration of an active injection or consultation. After the operation completes, the key MUST be zeroed or released.

> **Open decision.** Phase 0 has four open encryption decisions (lock scope, key caching, migration flow, locked fallback). These will be specified normatively in v0.2 once the prototype work answers them.

## 8. Integrity and Portable Export

### 8.1 In Place Integrity

AES-GCM provides authenticated encryption. Decrypt failure MUST be treated as an integrity failure and MUST NOT be retried with degraded checks.

### 8.2 Portable Export

An artifact exported for portability — for example, encoded in a QR code for device to device handoff — MUST be wrapped in a portable export object. Both fingerprint and user configuration use the same wrapper. The `mode` field discriminates two export modes with different trust models. When exporting a paired set, producers MAY emit two export objects (one per artifact) or a single combined export object that contains both; v0.1 specifies only the single artifact form below. The combined form is deferred to v0.2.

**Bootstrap mode.** Bootstrap export seeds a vault device that has no prior pairing with the producer — the first handoff, before any shared key exists. Because no key material has been established, the artifact is carried in cleartext:

```json
{
  "phaedo_export_version": "0.1",
  "mode": "bootstrap",
  "artifact": { ... },
  "pairing_token": "<opaque producer-generated token>",
  "digest": "base64url(32 bytes)"
}
```

`artifact` is the cleartext artifact document (Section 4 or Section 5). `digest` is SHA-256 over the canonical serialization (Section 6) of the export object with the `digest` field omitted. The digest is keyless: it gives tamper-evidence and detects transport corruption — for example, mis-assembled QR chunks — but NOT authenticity. It does not prove who produced the export.

`pairing_token` is an opaque value the producer also retains locally. The scanning device echoes it in the subsequent pairing handshake, where Section 7 key material is established, binding the out-of-band scan to the authenticated channel. Once that handshake completes, all further transfers use backup mode or the authenticated session channel — the cleartext window is exactly one scan wide.

A producer MAY include additional fields carrying its own pairing-handshake material — for example, `ext_pub`, an identity public key the consumer uses for out-of-band MITM detection. The digest covers every field except `digest` itself, so any such field is integrity-checked on receipt.

Bootstrap mode's trust model is physical: the export is displayed transiently, in the subject's presence, and scanned by a device the subject controls. The security boundary is camera line of sight. A producer MUST NOT use bootstrap mode for at-rest storage or for any transfer that is not a live, in-person handoff; a persisted bootstrap object is an unprotected plaintext artifact.

**Backup mode.** Backup export produces a durable, portable copy of an artifact that the subject custodies themselves — the lost-phone recovery path. Because the vault device holds its key material in non-extractable hardware, that key does not survive the device, so a backup a replacement device could actually open cannot be sealed under it. Backup mode is therefore **zero-knowledge and user-custodied**: the artifact is sealed under a freshly generated, high-entropy **recovery code** that the producer surfaces once for the subject to save (a password manager or their own storage) and never retains. There is no escrow — losing both the recovery code and the backup is unrecoverable, the accepted tradeoff of a no-cloud, no-accounts, keys-never-leave-the-device design. The artifact is wrapped in a Section 7 envelope:

```json
{
  "phaedo_export_version": "0.1",
  "mode": "backup",
  "envelope": { ... },
  "hmac": "base64url(32 bytes)"
}
```

The recovery code carries at least 160 bits of entropy, rendered in Crockford base32 for legible transcription. Two domain-separated keys are derived from it directly by HKDF — no PBKDF2 stretching, which is only needed for low-entropy human passphrases (Section 7.4 path 1): the AES-256-GCM key that seals the `envelope` (KDF context `phaedo:export:backup:v0.1`) and the HMAC-SHA-256 key for the tag below (context `phaedo:export:hmac:v0.1`).

The `hmac` field is HMAC-SHA-256 over the canonical serialization of the `envelope` object under the recovery-code-derived HMAC key. It is informative, not a substitute for the envelope's GCM tag: its purpose is to detect transport corruption and to confirm the presented recovery code is the one the backup was sealed under — a constant-time check made before AES-GCM decryption is attempted. A restore MUST verify the HMAC first and MUST treat any mismatch, exactly like a GCM tag failure, as an integrity failure that yields no plaintext and is not retried with degraded checks.

**Mode selection.** Backup mode is the durable, at-rest export: a producer MUST use it for any artifact written to storage the subject retains, since its cleartext window is zero. Bootstrap mode's cleartext is permitted only for the transient, in-person pre-pairing handoff (above) and MUST NOT be persisted.

Bootstrap mode's cleartext trust model is camera line of sight (above). A producer MUST NOT use bootstrap mode for a handoff that does not transit a private out-of-band channel the subject controls — in particular, it MUST NOT carry the cleartext artifact over a relay or any other infrastructure path. The pairing-code rendezvous in Section 8.4 is the relay-safe alternative.

### 8.3 Asymmetric Signing (Specified; not yet emitted)

Signing lets an artifact be presented to a party that never paired with the subject's vault — for example, an employer verifying that an employee's fingerprint was produced by a specific Anamnesis instance. This section specifies the scheme. **The v0.1 reference implementation does not yet populate `signatures`, and v0.1 producers MUST NOT populate it** (`fingerprint.schema.json` enforces this as `maxItems: 0`). What follows is the contract a v1.0 producer implements.

**Algorithm: ECDSA on NIST P-256 with SHA-256 (ES256).** Earlier drafts of this section named Ed25519. That was revised, because it conflicts with the key-custody requirement below: the iOS Secure Enclave supports P-256 only and cannot hold an Ed25519 key at all, so "Ed25519, in hardware" is not a buildable combination on the reference vault device. ES256 loses nothing in interoperability — it is a first-class W3C Verifiable Credential and JOSE signature suite, as widely supported as EdDSA. An implementation on a platform whose secure element offers a different curve MAY specify an additional algorithm, but P-256 is the interoperable baseline a verifier can assume.

**Key custody is the load-bearing requirement, not the algorithm.** The subject's signing key MUST be generated inside the vault device's secure element and MUST be non-extractable — never exported, never present in application memory, never written to general-purpose storage. A signature asserts to a third party that the subject's trust anchor produced the artifact; a key that ordinary application code could read would not support that assertion, and a scheme that permits a software-held key silently weakens every signature made under it. The key is **device-bound**: it MUST NOT be included in a Section 8.2 backup, and MUST NOT be reconstructible from one. A replacement device establishes a new signing identity and republishes its public key; identity is re-established, never transported. (This is the same boundary Section 8.2 draws — a backup restores what the subject *knows*, not what the device *is*.)

**Signing input.** The signature is computed over the Section 6 canonical serialization (RFC 8785) of the signed object with the `signatures` field itself omitted — the same construction Section 8.2 bootstrap mode already uses for `digest`. Omitting the field is what makes the input well defined regardless of how many signatures are later appended.

**Verification is independent of key discovery.** This section specifies how to verify a signature given the subject's public key; it does NOT specify how a verifier who never paired obtains that key in the first place. A paired client already holds it. For an unpaired third party — the employer case above — key distribution is an open problem (publication, attestation, and revocation are all unresolved), and it is deliberately left unspecified here rather than papered over: a signature scheme whose key discovery is undefined is verifiable between parties that already trust each other, and no more than that. See Section 13 (OQ9).

### 8.4 Pairing-Code Rendezvous and Encrypted Seed

A producer MAY establish the initial pairing without a QR handoff. In this mode the out-of-band channel is a short, single-use **pairing code** the subject reads from the producer and types into the vault device, rather than a scanned code.

The pairing code is a rendezvous and correlation value only. It carries no key material and no artifact. Its sole functions are (1) to let the two devices find each other (for example, as the lookup key for a relay offer) and (2) to bind the subsequent pairing handshake to this attempt. It is not a confidentiality control and not the man-in-the-middle control; the Short Authentication String (SAS) derived in the Section 7 handshake is. A producer MUST generate the code with a cryptographic RNG, give it a short expiry, and accept it for exactly one pairing.

Two rendezvous channels are defined, distinguished by whether the pairing handshake reaches the vault device directly or through untrusted infrastructure:

- **Direct (local network).** When the producer reaches the vault device over a local channel it can enumerate itself (for example, LAN discovery of the vault's pairing endpoint), the vault device MAY accept the pairing handshake without a pre-shared code: physical local-network access plus the user's SAS confirmation is the gate. This is the no-typing path.
- **Relayed.** When the handshake is carried by a relay or any channel reachable beyond the local network, the vault device MUST require a matching pairing code before presenting an SAS confirmation, so that an arbitrary remote party cannot trigger confirmations. This is the typed-code fallback.

In both channels the SAS is the man-in-the-middle control and the user's confirmation is the authorization. A vault device MUST NOT revoke or disturb an existing pairing on the basis of an unconfirmed pairing request. A vault device MAY hold **multiple concurrent verified clients** (for example, a browser extension and a local MCP server); confirming a new pairing **adds** a client and MUST NOT revoke or displace any other. Each client is approved independently by its own SAS confirmation and is independently revocable; a client is removed only by explicit user revocation, or by denial of its own pairing request.

Because no QR carries the producer's identity public key, that key (`ext_pub`) travels in the pairing handshake request itself. Substitution of either party's long-term public key in transit is detected by the SAS: both devices derive the SAS from both long-term public keys and the subject compares the two displayed strings before confirming. A producer and consumer MUST surface the SAS for comparison and MUST NOT complete pairing until the subject confirms it.

The artifact is not carried during rendezvous. Once the handshake establishes an SAS-verified `pair_key`, the producer transfers the artifact as a **seed envelope**: a Section 7.2 encryption envelope delivered to the vault device over the authenticated channel (for example, a dedicated pairing endpoint). The envelope's metadata carries `artifact_kind` and, for a fingerprint, `fingerprint_id`, bound as AAD. The consumer MUST treat a decryption failure as an integrity failure (Section 8.1) and MUST reject a seed from a client that has not been confirmed (`verified`). Because the artifact is encrypted under a key the relay never holds, no cleartext artifact crosses relay infrastructure — the confidentiality property the camera channel previously provided.

The seed envelope's key is `seed_key`, a domain-separated sub-key of the pair key:

```
seed_key = HKDF-SHA-256(ikm = pair_key, salt = "", info = "phaedo-seed-v0.1", L = 32)
```

`seed_key` is derived from `pair_key` rather than reusing it directly so that the AES-256-GCM seed key is never the same octets as the HMAC key `pair_key` carries in the Section 7 authorize exchange. Both parties re-derive `seed_key` on demand from the stored `pair_key`; it is not transmitted.

```json
{
  "phaedo_envelope_version": "0.1",
  "alg": "AES-256-GCM",
  "iv": "base64url(12 bytes)",
  "ciphertext": "base64url(...)",
  "tag": "base64url(16 bytes)",
  "metadata": { "artifact_kind": "fingerprint", "fingerprint_id": "<uuid>", "created_at": "<rfc3339>" }
}
```

The seed envelope reuses the Section 7.2 structure verbatim; only the key selection (the `pair_key` rather than a session or master-derived key) and the one-time pre-seed use distinguish it.

## 9. Injection Protocol

The injection protocol describes how a consumer requests a fingerprint projection suitable for inclusion in an AI session as system prompt or context.

### 9.1 Injection Modes

Two modes are defined. Both modes operate on the combined projection (selected fingerprint layers, standing instructions from the paired user configuration, and selected examples; see Section 5.4).

1. **Standard mode.** The injection adapter receives plaintext content: layer projections, standing instructions verbatim, and selected examples. This is the default and is what the reference Chrome extension uses. As of Proposal 0007 the reference consumer (`context-block.js`) renders the standing instructions carried in `phaedo_fingerprint.standing_rules` (those with `text`) **verbatim** as a top-of-projection **"Operating rules (user-confirmed)"** block — above the inferred-style sections, so a confirmed rule wins where it conflicts with an inferred habit (§4.3), ordered by §5.2 `priority` and applied silently (not restated).
2. **Enhanced privacy mode (Stained Glass).** The injection adapter receives an obfuscated payload designed to preserve persona signal while removing identifying detail. The obfuscation **algorithm** is proprietary and out of scope; the **interface** — payload envelope, the guarantees a producer asserts, and how a third party proves conformance — is normative as of v0.1.51 and specified in §9.6.

A consumer MAY request enhanced privacy mode. A producer MAY refuse if it does not support the mode. Refusal is a structured error, not a silent fallback to standard mode.

> **Note on configuration injection in the request and response shapes.** Section 9.2 and 9.3 show fingerprint-only fields. Substantive integration of configuration into the request and response is tracked as a separate decision (see change log v0.1.1) and is expected in v0.2.

### 9.2 Injection Request

```json
{
  "phaedo_request_version": "0.1",
  "request_type": "injection",
  "session_context": {
    "platform": "claude_web",
    "domain": "finance",
    "task_hint": "drafting a strategic memo",
    "audience_hint": "investor",
    "max_tokens": 2000
  },
  "mode": "standard",
  "requested_layers": ["all"],
  "consumer_id": "phaedo_chrome_extension_v0.1.3"
}
```

| Field | Required | Description |
|---|---|---|
| `request_type` | yes | One of `injection`, `consultation` (Section 10). |
| `session_context` | yes | Cleartext hints about the session. Used for layer selection and Section 5.2 scope activation. The optional `domain` field (added v0.1.42) declares the session's domain in the same case-insensitive substring namespace as `match.domains`; `task_hint` additionally drives `task`-scoped instruction activation. MUST NOT include subject content. |
| `mode` | yes | `standard` or `enhanced_privacy`. |
| `requested_layers` | yes | Array of layer names, or `["all"]`. |
| `max_tokens` | no | Soft cap on the size of the projection. Producer SHOULD honor; MAY exceed if a smaller projection would be unusable. |
| `consumer_id` | yes | Identifier of the requesting software. |

### 9.3 Injection Response

```json
{
  "phaedo_response_version": "0.1",
  "request_type": "injection",
  "fingerprint_id": "f1b9c4e2-7d3a-4e8b-9c0f-2a1b3c4d5e6f",
  "mode": "standard",
  "projection": "<plaintext system prompt content>",
  "layers_included": ["surface", "domain_and_expertise", "decision_and_risk", "big_picture"],
  "persona_strength": 0.62,
  "expires_at": "2026-04-28T18:00:00Z"
}
```

The `projection` field is the content the consumer inserts into the AI session. For standard mode, this is human readable text. For enhanced privacy mode, this is the obfuscated representation; format is producer specific in v0.1.

`expires_at` is a soft hint. Consumers SHOULD discard the projection after expiry and request a fresh one for a new session.

### 9.4 Layer Selection

In v0.1, layer selection is producer driven. The producer reads the session context hints and chooses which layers to project. A future version may expose a layer selection negotiation protocol; v0.1 does not.

Producers SHOULD document the selection logic so consumers can predict behavior. The reference implementation publishes its selection rules separately.

### 9.5 Errors

Errors are returned as:

```json
{
  "phaedo_response_version": "0.1",
  "request_type": "injection",
  "error": {
    "code": "mode_not_supported",
    "message": "Enhanced privacy mode is not available in this build."
  }
}
```

Error codes for v0.1:

- `mode_not_supported`
- `layer_not_available`
- `decryption_failed`
- `persona_strength_below_threshold`
- `request_malformed`
- `internal_error`

### 9.6 Enhanced Privacy Interface (Stained Glass)

*Normative as of v0.1.51. Resolves OQ12.*

Some subjects cannot send a plaintext persona projection to a vendor-hosted model at all — a clinician, a lawyer, an employee under an enterprise DLP policy. For them the choice today is "no Anamnesis" or "policy violation." Enhanced privacy mode exists so a producer can hand a consumer a projection that carries the *behavioral* signal without the *identifying* detail.

**What this section specifies, and what it does not.** The obfuscation algorithm is out of scope — deliberately and permanently. A conformant enhanced-privacy producer may use redaction, paraphrase, k-anonymization, synthetic restatement, a local model, or anything else. What is normative here is the **interface**: the payload shape a consumer receives, the guarantees the producer asserts about it, and the check a third party runs to prove an implementation conforms. This is the same split the standard uses elsewhere: the shape is public so the ecosystem can interoperate, the mechanism is the implementer's.

#### 9.6.1 Response payload

An enhanced-privacy §9.3 response carries the ordinary fields, with `mode: "enhanced_privacy"` and `projection` holding the obfuscated text. It MUST additionally carry `privacy`:

```json
{
  "phaedo_response_version": "0.1",
  "request_type": "injection",
  "fingerprint_id": "f1b9c4e2-...",
  "mode": "enhanced_privacy",
  "projection": "<obfuscated projection text>",
  "layers_included": ["decision_and_risk", "behavioral"],
  "persona_strength": 0.62,
  "expires_at": "2026-04-28T18:00:00Z",
  "privacy": {
    "profile": "stained_glass/v1",
    "producer": "phaedo-reference/0.2.2",
    "preserved": ["decision_and_risk", "behavioral"],
    "removed": ["domain_and_expertise.primary_expertise", "big_picture.anything_else"],
    "signal_retention": 0.71,
    "reversible": false
  }
}
```

| Field | Type | Required | Description |
|---|---|---|---|
| `profile` | string | yes | Obfuscation profile identifier, `name/version`. Opaque to the protocol; names the *contract*, not the algorithm. Consumers MUST NOT branch on it beyond logging and policy checks. |
| `producer` | string | yes | Implementation that produced the payload, `name/version`. |
| `preserved` | array of strings | yes | Layers (or `layer.field` paths) the producer asserts still carry usable signal. |
| `removed` | array of strings | yes | Layers or `layer.field` paths deliberately withheld or destroyed. A consumer MUST treat these as absent, not as empty. |
| `signal_retention` | number `[0,1]` | yes | The producer's own estimate of retained persona signal relative to the standard-mode projection. Self-asserted, not protocol-verified — see §9.6.3. |
| `reversible` | boolean | yes | Whether the producer retains any mapping that could re-identify the removed content. **A conformant enhanced-privacy payload SHOULD be `false`.** A `true` value MUST be surfaced to the subject: it means the obfuscation is a display convenience, not a privacy guarantee. |

#### 9.6.2 Producer guarantees

A producer asserting `mode: "enhanced_privacy"` MUST guarantee:

1. **No episodic content.** The obfuscated projection MUST NOT contain URLs, email addresses, domain names, personal names, employer names, or case/matter identifiers. This is the §4.6 layer-admission rail applied to the *rendered output*, and it is mechanically checkable (§9.6.3).
2. **No re-identification through examples.** §5.3 example-corpus content is verbatim subject writing and is therefore **excluded by default** under enhanced privacy. A producer that includes transformed examples MUST list `example_corpus` in `preserved` and MUST NOT reproduce any span of 8 or more consecutive words from the original.
3. **Authored rules are content, not style.** §5.2 standing instructions are authored prose that may name employers, matters, or people. A producer MUST either omit them (listing `standing_instructions` in `removed`) or obfuscate them under the same rails as layer content. It MUST NOT pass them through verbatim, notwithstanding §5.2's verbatim requirement — that requirement is a *standard-mode* guarantee.
4. **Honest accounting.** Every layer that contributed to `projection` appears in `preserved`; every layer requested but withheld appears in `removed`. Silent omission is a conformance failure — it is what makes a consumer believe it has coverage it does not have.
5. **No silent downgrade.** A producer that cannot meet these guarantees MUST return `mode_not_supported` (§9.5) rather than returning standard-mode plaintext under an enhanced-privacy flag. This is the single most important rule in this section: a silent downgrade sends the plaintext the subject specifically asked not to send.

#### 9.6.3 Conformance check

Enhanced privacy is claimed at the §11 level the implementation otherwise claims, with an added suffix (e.g. "Anamnesis Level 1 Compatible, Enhanced Privacy"). The check is deliberately mechanical, because the interesting property (signal preservation) is not mechanically checkable and must not pretend to be:

- **Structural.** `privacy` present and complete; `preserved` ∪ `removed` covers every layer in `layers_included`; `signal_retention` ∈ [0,1]; `reversible` present.
- **Leakage.** The rendered `projection` passes the §4.6 episodic-content rail (the same regex family `phaedo-validate` applies to layer values and summaries) plus a name/employer check against a supplied identity set.
- **Non-downgrade.** Given a fingerprint the producer cannot obfuscate, it returns `mode_not_supported` — never plaintext.
- **Example non-reproduction.** If `example_corpus` ∈ `preserved`, no 8-word span from the source corpus appears in `projection`.

`signal_retention` is **not** verified by the conformance suite. It is a self-assertion, and the standard says so plainly rather than implying a guarantee it cannot enforce. A benchmark that measures retained signal against paired outcomes (the persona-effectiveness methodology) is the honest way to check it, and it is out of scope here.

#### 9.6.4 Reference implementation status

The reference implementation returns `mode_not_supported` for `enhanced_privacy` (`spec/conformance.json` reports `enhanced_privacy_mode_stained_glass: false`, and TC-INJ vector `T-PHAEDO-INJ-0003` locks that behavior). This section exists so a third party — or a future proprietary Phaedo build — can implement the mode against a stable, published contract rather than inventing one.

## 10. Agent Consultation Protocol

> **Status:** Implemented in the reference MCP server (`phaedo_consult`, all four types; Section 10.5 policies; the `insufficient_signal` abstain outcome as of v0.1.9). The request (10.2) and response (10.3) shapes are **stable** and may be built against; committed to v1.0. *How* a consumer derives the signal — a deterministic rule engine, a local model judge, or both — is implementation, not protocol. The reference implementation separates a **pure deterministic resolver** (`mcp/consult-core.js`, `resolveConsultationCore(vd, request)` — the publishable open-core surface) from the optional local model judge and transport (`mcp/consult.js`).

The consultation protocol lets an autonomous agent query the fingerprint at decision points without ingesting the full fingerprint.

### 10.1 Consultation Types

| Type | Purpose |
|---|---|
| `action_approval` | Should the agent proceed with a specific action? |
| `voice_draft` | Generate a draft in the subject's voice for a given task. |
| `domain_risk_check` | What is the subject's risk tolerance and evidence threshold in this domain? |
| `escalation_default` | When uncertain, what should the agent default to (proceed, ask, escalate)? |

### 10.2 Consultation Request

```json
{
  "phaedo_request_version": "0.1",
  "request_type": "consultation",
  "consultation_type": "action_approval",
  "agent_id": "vendor_agent_v2.4",
  "action_descriptor": {
    "domain": "financial",
    "reversible": false,
    "magnitude": "high",
    "summary": "Approve $12,000 vendor payment outside standard terms."
  },
  "action_binding": {
    "tool_name": "issue_payment",
    "arguments_hash": "9f2a41c0b7de5581aa30e6c4b8f17d29",
    "arguments_preview": "payee=ACME Corp, amount=12000, currency=USD"
  },
  "context": {
    "deadline_pressure": "low",
    "evidence_provided": ["invoice", "po_match"]
  }
}
```

**The action descriptor is untrusted input.** Every field a resolver decides on — `domain`, `reversible`, `magnitude`, `amount`, `summary` — is authored by the agent being gated. A resolver MUST treat the descriptor as the requesting agent's *claim* about the action, never as a verified property of it. A buggy, prompt-injected, or hostile agent can satisfy any `match` by describing its action differently, and a subject who approves an escalation is approving the agent's account of the action unless something else is presented alongside it.

**`domain` and the published vocabulary.** `domain` is a free-text string chosen by the agent, and everything downstream keys on it: §10.5 rule matching, the §10.6 receipt, and the §10.7 approval counts that decide whether autonomy is ever proposed. Two spellings of one concept therefore become two classes, and the subject's evidence splits between them — observed in the reference deployment as `financial`, `finance` and `finance.crypto_trading` for a single domain, with the approvals split so that no class reached the §10.7 threshold.

`spec/domains.json` publishes a **canonical vocabulary**: a set of domain identifiers, each with a list of aliases. A resolver SHOULD resolve a `domain` to its canonical term before recording it on a §10.6 receipt or counting it as promotion evidence.

- **Free text remains valid.** An unrecognized domain MUST be recorded and matched exactly as before. The vocabulary confers identity; it is not an enum and not a gate, and a resolver MUST NOT reject a request for using a domain outside it.
- **Aliases are SYNONYMS, never GENERALIZATIONS.** An alias asserts *the same concept at the same risk*. A child→parent mapping (`crypto_trading` → `finance`, `paralegal` → `legal`) MUST NOT be published as an alias, because a grant authored for the general class would then silently cover a narrower, riskier one the subject never demonstrated. This is why `investing` is a distinct term rather than a `finance` alias — a spending guardrail and a trading guardrail are not the same authority — and why domains absent from the vocabulary simply do not merge.
- **The vocabulary is PUBLISHED, not private.** The alternative — a synonym table living inside a resolver — would place decision semantics somewhere the subject cannot read and a third party cannot reproduce. An implementation that embeds a copy for packaging reasons MUST keep it identical to the published file and SHOULD enforce that mechanically.
- **Canonicalization is bounded by where it can do harm.** See §10.5: an alias may widen a *guardrail's* reach but never a *grant's*.

Presentation-only normalization (case, surrounding and internal whitespace) is always safe and SHOULD be applied universally; it asserts nothing about meaning.

**`action_binding` (OPTIONAL).** Binds the consultation to the concrete call the descriptor claims to describe.

- **`tool_name`** (REQUIRED within the object) — the tool or function about to be invoked.
- **`arguments_hash`** (REQUIRED within the object) — a hex or base64url digest over the Section 6 canonical form of the arguments. The arguments themselves MUST NOT be transmitted.
- **`arguments_preview`** (OPTIONAL) — a short human-readable rendering, for display to the subject on an escalation. Advisory text, never a resolution input.

A binding does **not** make the descriptor truthful; nothing at this layer can, short of the resolver executing the call itself. It is a *commitment device* with three effects: (1) the §10.6 receipt records the tool and argument digest, so a descriptor/action mismatch becomes provable after the fact against the agent's own logs; (2) an escalation carries the real call to the subject beside the agent's prose (§10.7); and (3) an authorization may require it before relaxing anything (§10.5 `require_binding`), bounding the blast radius of a fabricated descriptor to what the subject explicitly opted into.

A request that omits `action_binding` is valid and resolves exactly as in prior revisions. A request that includes it MUST be rejected with `request_malformed` if the object is structurally invalid — a half-formed binding is worse than none, because a caller may believe it is bound when the resolver treats it as unbound.

Producers SHOULD send a binding whenever the consultation precedes a concrete call, and MUST send one to benefit from a `require_binding` authorization.

### 10.3 Consultation Response

```json
{
  "phaedo_response_version": "0.1",
  "request_type": "consultation",
  "consultation_type": "action_approval",
  "signal": "escalate",
  "confidence": 0.78,
  "rationale_hint": "Subject's pattern in irreversible financial actions above $5K is to require human review.",
  "deference_level": "low"
}
```

`signal` is one of:

- `proceed` — pattern aligns with action
- `proceed_with_note` — pattern aligns but flag for after the fact review
- `clarify` — agent should gather more evidence before acting
- `escalate` — surface to subject for live decision
- `decline` — pattern actively opposes action
- `insufficient_signal` — **abstain.** The producer declines to answer because the fingerprint lacks adequate coverage or confidence for this `action_descriptor` domain. Distinct from `clarify` (which asks the *agent* to gather more evidence and re-ask) and from an error (the request was well formed; the answer is "no basis"). A consumer SHOULD treat `insufficient_signal` as "no signal — fall back to your own default or escalate to the subject," not as a reason to retry. Conventionally paired with `deference_level: low`. A confidently wrong `proceed` is the worst output this protocol can produce; abstaining is preferred to guessing.

`deference_level` indicates how strongly the agent should weight the signal:

- `high` — strong pattern match, high confidence; agent SHOULD follow
- `medium` — pattern present but ambiguous; agent SHOULD weigh signal alongside other inputs
- `low` — sparse data; signal is a hint, not a directive

### 10.4 Consultation Boundaries

A consulting agent MUST NOT request the full fingerprint via the consultation API. The consultation API returns only signals, not layer content. Agents that need fingerprint content MUST go through the injection API and accept the corresponding boundaries.

### 10.5 Consultation Policies (deference tuning)

The subject MAY author standing **consultation policies** — per-domain / per-magnitude / per-reversibility guardrails that the consumer applies on top of the inferred signal. Policies are authored content (subject-confirmed, like §5 standing instructions), so they **override** the inferred consultation signal: they encode hard pre-decisions ("always escalate irreversible spend or legal", "auto-proceed low-stakes reversible writing") that make delegation safe. Policies travel with the subject (carried alongside the fingerprint) and are applied locally; they never expand the §10.4 boundary (the response shape is unchanged — policy provenance is conveyed in `rationale_hint`).

A policy document is a list of rules:

```json
{
  "version": "0.1",
  "rules": [
    { "id": "irreversible-spend-legal",
      "match": { "domains": ["financial", "legal", "payment"], "reversible": false },
      "effect": "escalate",
      "note": "Irreversible money or legal actions always go to a human" },
    { "id": "low-stakes-writing",
      "match": { "domains": ["writing", "draft", "email"], "magnitude_max": "medium", "reversible": true },
      "effect": "autoproceed",
      "note": "Low-stakes reversible writing is pre-approved" }
  ]
}
```

- **`match`** (all present constraints must hold): `domains` (substring match, case-insensitive, on the action descriptor's domain), `magnitude_min` / `magnitude_max` (`low` | `medium` | `high`), `reversible` (`true` | `false`), and the two numeric bounds `amount_gt` / `amount_lt`.
  - **`amount_gt`** is a **floor**: matches only when the descriptor carries an `amount` strictly greater than it — "escalate irreversible spend over 5000".
  - **`amount_lt`** is a **ceiling**: matches only when the descriptor carries an `amount` strictly less than it — "auto-proceed reversible purchases under 75". Present both for a band; both must hold.
  - An action with **no** `amount` satisfies **neither** bound. This is the important case for a ceiling: an unpriced action MUST NOT slip under a cap that cannot be checked. Because both bounds fail closed on a missing amount, adding either to a rule can only ever *narrow* it.
  - Strict comparison on both sides is deliberate. An action exactly at a ceiling does not match, so it falls through to the ordinary consultation — the fail-safe direction.
- **`effect`**: `escalate` / `require_human` (force `escalate`), `decline` (force `decline`), `autoproceed` (force `proceed`); or `bias_cautious` / `bias_bold` (nudge the signal one step along `proceed → proceed_with_note → clarify → escalate`).
- **`require_binding` (optional, default `false`).** When `true`, this rule applies to a request only if that request carries a valid §10.2 `action_binding`. It is enforced **only for authority-expanding effects** (`autoproceed`, `bias_bold`): a rule that makes the agent *more* deferential MUST keep applying whether or not the request is bound, or the gate would itself become a way to shed a guardrail by omitting a field. The direction is always authority-narrowing, matching `expires_at`. A resolver SHOULD report that a relaxing rule was withheld for want of a binding (via `rationale_hint`), so an agent can discover that it needs to send one rather than observe a rule silently failing to fire. Subjects SHOULD set `require_binding: true` on any new `autoproceed` authorization; a producer that *proposes* an authorization MUST set it.
- **Conditional + revocable authority (optional).** `expires_at` (RFC 3339) makes an authorization **time-bound**: once it passes, the rule has LAPSED and no longer applies — an identity-free, fail-safe form of revocation (the inferred resolution simply stands). It is **enforced** by the reference resolver (a lapsed force or bias rule stops applying).
- **Revocation after the fact — `revoked` tombstones (optional, ENFORCED).** `expires_at` lapses an authorization on a schedule the subject set *in advance*; taking one back *afterwards* is a different operation, and on a multi-device deployment it cannot be expressed by deletion alone. Guardrail sets reconcile by **union** across devices — losing an explicit decision is never acceptable — and a union cannot represent a removal: dropping a rule on one device is simply undone by the other device's copy at the next sync, so the revocation **silently fails**. A policy document therefore MAY carry a `revoked` list of **tombstones**, each naming the identity of a rule the subject removed. A consumer **MUST** drop any rule whose identity appears there, and a merge **MUST** union tombstones from **both** sides — a revocation the other device has not yet seen must still take effect. Three constraints keep it honest. **(1) Fail-closed:** a tombstoned identity stays revoked even if a rule bearing it reappears (from a restored §8.2 backup, say), because a revoked `autoproceed` returning to life is the harmful direction, and rule ids are unique-by-construction so a genuine new rule never collides. **(2) Identity must be computed identically** by every implementation — the rule's `id`, or for a legacy id-less rule the same content-derived key the merge dedupes on — or the tombstone will not match the rule it is meant to kill. **(3) Tombstones MAY be capped by COUNT but MUST NOT be pruned by age**: a device that synced before the prune would resurrect the rule, which is the exact failure the mechanism exists to prevent. A single-device implementation that never syncs may delete outright and remains conforming.
- **Domain matching, and the vocabulary asymmetry.** A rule's `match.domains` covers an action when either (a) the action's normalized domain contains one of the rule's — the substring rule, unchanged — or (b) **for a restrictive effect only**, the action and the rule resolve to the same §10.2 canonical term. Path (b) is **denied to authority-expanding effects** (`autoproceed`, `bias_bold`) deliberately: an alias table is a human judgement about meaning, and a wrong entry must never hand an agent autonomy the subject did not grant. It may only ever make a *guardrail* cover more. So the worst case for a mistaken alias is "an agent asks when it needn't" — never the reverse, and never a lost guardrail, since (b) is purely additive to (a). A resolver that publishes no vocabulary implements (a) alone and remains conforming.
- **Per-client scoping — `agents` (optional, ENFORCED).** `agents` scopes an authorization to specific **paired clients**. Entries are opaque, implementation-issued `client_id` values, **compared exactly** (case-sensitive), and they are matched against **the resolver's own pairing identity** — not against anything the caller supplied.
  - **Why the resolver's own identity, and not the agent's.** A resolver serves exactly one paired client, so it never has to *ask* who is calling: it knows who it **is**, from its own pairing record. Nothing agent-supplied enters the decision, which is precisely what makes this enforceable where `agent_id` is not. The pairing was established out-of-band with a second device under user verification, so a co-resident process cannot forge it by asserting a string — the failure mode that makes a locally-held credential close to meaningless (see also OQ9).
  - **`agent_id` is not a gate.** It remains **self-asserted and untrusted** — an audit label recorded on the §10.6 receipt, exactly as `action_descriptor` is treated since v0.1.48. A conforming resolver **MUST NOT** match a §10.5 authorization against `agent_id`.
  - **Narrowing-only.** Scoping is enforced **only for authority-EXPANDING effects** (`autoproceed`, `bias_bold`). A restrictive effect (`escalate` / `require_human` / `decline` / `bias_cautious`) keeps applying regardless of scope — otherwise `agents` would become a way to *shed* a guardrail by running an unlisted client. Same direction as `expires_at` and `require_binding`.
  - **Fail-safe.** For a relaxing rule, an unlisted or **unpaired** resolver makes the rule **inert** — "does not apply", never "applies more broadly", and never an error. A caller with no established identity therefore has nothing to match, so scoped authority is simply not extended to it. A malformed `agents` (present but not an array) is likewise inert for a relaxing effect rather than an error.
  - **ABSENT and EMPTY are different, and the difference is load-bearing.** Omitting `agents` leaves the rule **unscoped** — it applies to every client. An **empty array** is a scope that names *no* client, and therefore matches none. An authoring surface where the subject deselects every client MUST write `[]` and MUST NOT omit the field; collapsing the two would silently turn "nobody may do this without asking" into universal autonomy, in the widening direction. Entries MUST be strings; a conforming resolver drops non-string entries rather than coercing them (coercion would invent principals — `[42]` becoming a rule that matches a client whose id is `"42"`).
  - **Not exportable to a format that cannot carry the scope.** A scoped grant MUST NOT be serialized into an external credential that has no vocabulary for the scope (e.g. the §12 AP2 Intent Mandate profile). Emitting it unscoped would assert to a third party an unconditional grant the subject made to exactly one client. Withholding the credential is the correct rendering — the same reason a restrictive rule produces no mandate rather than a restrictive one.
  - **Silent by design (§10.4).** A resolver **MUST NOT** disclose that a scope-inert rule exists. Unlike the `require_binding` case — a fixable omission worth reporting to the agent — telling an unlisted client that some rule would have relaxed for a *different* client would leak the shape of the subject's other grants.
  - **Boundary, stated plainly.** This does **not** defend against a process that has already read the resolver's pairing record: at that point it holds the pairing key and *is* that client for all purposes. File secrecy and revocation on the subject's device are the controls there. No scoping scheme survives key theft, and this one does not pretend to.
  - **Authoring is device-side.** A subject cannot be expected to type an opaque `client_id`. The implementation holding the client registry (in the reference, the phone) writes the identifier and displays the friendly label.
- **Force effects are authorizations.** A matched force effect is an authored, deterministic pre-decision: it resolves the consultation **canonically**, overriding the inferred signal, at `confidence: 1.0` and `deference_level: high`. Because it is authored content (subject-confirmed, §5.6 semantics), it is canonical over any inferred pattern, the same way an authored anti-preference is canonical over an inferred one (§4.3). A `bias_*` effect is a softer nudge and keeps the inferred confidence.
- **Precedence**: the first matching force-effect rule wins; otherwise the first matching bias applies. A force effect's `note` (or a default) is surfaced as the `rationale_hint`, so the agent sees *why* (e.g. "Per your standing rule: …").
- **Authored only.** Policies are authored content: a producer MUST confirm them with the subject before commit (§5.6) and MUST NOT infer or suggest them from observation. In the reference implementation the extraction pipeline has no write-path into `consult_policies` or `standing_rules` (locked by `scripts/test_consult_policies_invariant.mjs` and `scripts/test_standing_rules_invariant.mjs`).
- Policies MUST NOT apply to `voice_draft` (a redirect, not a decision).
- **Portability**: policies SHOULD be carried **inside the fingerprint** so they travel with it across every transport with no profile-schema change. As of Proposal 0007 the home is `phaedo_fingerprint.standing_rules` with `kind:"authorization"` (carrying the same `match`/`effect`); the standalone `phaedo_fingerprint.consult_policies` array is **DEPRECATED** but still honored as a back-compat read path (removed in v0.2 with the §5 migration). A consumer MAY also accept policies as a sibling artifact or local configuration.
- **Authored decision rules as a bias (Proposal 0007 §D).** A `standing_rules` entry of `kind:"instruction"` is a verbatim injected rule, not a gate; when it carries a `decision` binding with **negative** polarity, the reference resolver also projects it to a `bias_cautious` nudge for matching-domain (`decision.domain`) actions. **The asymmetry is by design and permanent: an authored disposition may make the agent MORE deferential, never less.** Autonomy *expansion* (auto-proceed) is never inferred from a soft rule — it requires an explicit `kind:"authorization"` with `effect:"autoproceed"` and a `match` (domain / magnitude / amount), so the relaxation is deterministic, scoped, and auditable. Positive-polarity and unbound instructions therefore inject only and have no consultation effect.
- **Deterministic pre-flight (binding affordance).** A consumer MAY expose a deterministic-only check of the standing authorizations — match the `action_descriptor` against the force rules, skipping all inferred evaluation — so an agent can short-circuit on a hard guardrail before a full consultation. The reference MCP binding exposes this as the `phaedo_check_authorization` tool; its response shape is `spec/schemas/authorization-check-response.schema.json` and it honors §10.4 (only the rule's decision and provenance cross). This is a transport convenience over the same authorizations, not a new resolution path.

### 10.6 Consultation Receipts

A consultation producer SHOULD keep an encrypted, **append-only**, vault-held record of every resolved consultation — the subject's audit trail of which agent asked what and what the oracle answered, and the data layer for agreement tracking. **Receipts never leave the device.** Phaedo (the company) and any intermediary hold nothing.

Each receipt captures the request descriptor and the response **signal fields only** — never layer content, never the projection, never rationale text (the §10.4 boundary holds inside the vault too):

```json
{
  "receipt_id": "uuid-v4",
  "created_at": "2026-06-10T17:00:00Z",
  "via": "phaedo_consult",
  "agent_id": "vendor_agent_v2.4",
  "client_id": "c_ATFQrFdTjo",
  "request": {
    "consultation_type": "action_approval",
    "action_descriptor": { "domain": "financial", "reversible": false, "magnitude": "high", "amount": 12000, "summary": "Approve $12k vendor payment." }
  },
  "response": { "signal": "escalate", "confidence": 0.78, "deference_level": "high" },
  "user_action": null
}
```

Normative rules (machine form: `spec/schemas/consultation-receipt.schema.json`):

- **One receipt per resolved request**, abstains (`insufficient_signal`) included. Errors are not resolutions and produce no receipt. A matched deterministic pre-flight (§10.5 affordance) is a resolution and produces a receipt (`via` distinguishes it); an unmatched pre-flight is not.
- **`user_action` is the only mutable field.** `null` at write time; updated later when override data exists — `approved | rejected | modified | unknown` (what the subject actually did with the agent's action). Every other field is immutable after write. Receipts are never deleted individually; the store is bounded by a configurable cap (reference default 5,000) with oldest-first eviction, and is destroyed in whole with the account.
- **Two identities, believed to different degrees.** `agent_id` is **who claimed** to be calling — self-asserted, unverified, an audit label and never a gate. `client_id` is **who actually served** the call: the resolver's own paired-client identifier, established out-of-band under user verification and revocable by the subject, which is the identity §10.5 `agents` scoping matches on. Recording both is the point — the audit can then distinguish the paired client that acted from whichever vendor string it chose to claim, and a disagreement between them is itself a finding. `client_id` is `null` when the resolver is unpaired. Both are immutable after write.
- **`action_binding` (optional, recorded verbatim).** When the §10.2 request carried a binding, the receipt records it — `tool_name`, `arguments_hash`, and `arguments_preview` if present — as part of the immutable request record. This is what makes a later descriptor/action mismatch provable: the receipt states what the agent said it was about to run, and the agent's own logs state what it ran. Absent when the request was unbound.
- **`drivers` (optional provenance, §10.4-safe).** An inferred consultation MAY record the Decision&Risk cues that drove it — `{cue, lean?/value?, confidence, basis}` — so the subject can later audit *why* the oracle answered as it did and calibrate it. This is a LOCAL field of the encrypted receipt only; it MUST NOT appear in the §10.3 response the agent sees (§10.4), and it carries direction/confidence/evidence-basis, never raw layer text. Absent for deterministic pre-flights and abstains (no inferred cue basis). Reference: `consultDrivers()` (`mcp/consult-core.js`).
- **Encryption:** the standard Section 7 AES-256-GCM envelope under a key derived with the **distinct domain-separation context `phaedo:receipts:enc:v0.1`** — the receipt store and any other at-rest artifact are independent ciphertexts under one root.
- **Purity of the resolver:** receipt writing happens in the transport layer after resolution, never inside the resolver. A receipt-write failure MUST NOT fail the consultation itself.
- **Signed receipts (future).** Post-v1.0, the reserved §8.3 `signatures` field is the intended path to receipts a third party can verify ("this agent did consult the subject's oracle and received this signal") without seeing the fingerprint. v0.1 producers MUST NOT populate it.

### 10.7 Autonomy Promotion (proposing a relaxation)

Every other learning channel in this specification can only make an agent **more** deferential: §10.5 states that an authored disposition may never expand autonomy, and the delegation channel learns from the subject's *corrections*. Expanding autonomy requires the subject to author an `autoproceed` authorization by hand. In practice almost nobody does, so a conforming deployment accumulates friction and never sheds it — and an approval that has become reflex is neither meaningful consent nor a usable product.

A producer MAY therefore **propose** a §10.5 `autoproceed` authorization from a class of actions the subject has repeatedly approved. This is a proposal, not a grant: it is staged in the review queue (`suggested_rules`, `kind: "authorization"`, `source: "autonomy_promotion"`) and becomes authored content only through the subject's explicit endorsement, exactly as every other suggestion does. **A producer MUST NOT author an authorization directly**, and MUST NOT propose any effect other than `autoproceed`.

**Repetition is not consent.** A subject approving a run of actions in one sitting is exhibiting fatigue as readily as agreement, and promoting that would launder fatigue into autonomy. A producer proposing an authorization MUST therefore establish that the pattern reflects *deliberation*, not volume. The reference producer requires all of:

- **Spread** — approvals across several distinct days, not a single sitting.
- **No contrary evidence** — not one rejection or modification anywhere in the class. A class the subject has ever overridden is not settled.
- **Demonstrated fit** — the oracle's agreement rate in that domain is already high over a meaningful number of scored decisions. Autonomy MUST NOT be proposed for a domain in which the oracle is frequently overruled.
- **Not batch-recorded** — outcomes stamped together in one pass (see `user_action_at`, §10.6) are bookkeeping, and MUST NOT carry the majority of the supporting evidence.

**A proposed relaxation is bounded.** A producer MUST NOT propose an authorization that is not all of:

- **Reversible only** — `match.reversible: true`.
- **Magnitude-capped** — at most the highest magnitude actually observed, and never `high`.
- **Domain-scoped** — an unscoped `autoproceed` is a blank cheque.
- **Binding-gated** — `require_binding: true` (§10.5), so a fabricated descriptor cannot unlock it.
- **Time-bounded** — `expires_at` set, so an autonomy grant the subject stops wanting lapses on its own rather than persisting silently.

**A priced class MUST carry a ceiling.** Where any action in the class carries an `amount`, a proposed authorization MUST set `match.amount_lt`. The ceiling MUST NOT be the largest amount observed: a single outlier would then set the bar for everything after it. A producer MUST require the ceiling to have been demonstrated at least twice — the reference implementation uses the **second-highest** approved amount, which is the monetary form of the "spread across days, not one sitting" rule. A class with fewer than two priced approvals cannot justify a bound and MUST NOT be proposed.

An endorsing consumer SHOULD re-assert these constraints at the point of the authored write rather than trusting the staged object, which may have crossed a sync boundary. The reference implementation refuses to endorse a staged authorization that has lost its binding requirement, its expiry, its reversibility constraint, or its domain scope.

## 11. Conformance

### 11.1 Profiles and Levels

Profiles are grouped into three **conformance levels** by how much of the protocol an implementation must adopt. The level is the adoption floor: a higher level subsumes the capabilities of the lower ones.

| Level | Profile | Description | Required Sections | Crypto? |
|---|---|---|---|---|
| **0** | **Projection Consumer** | Reads an already-decrypted **projection** — the Section 9.3 response `projection` string, or the reference server's `phaedo://fingerprint/projection` resource — and inserts it into a session. Consumes a string. | 9.3 (response shape) | **None** |
| **1** | **Consumer** | Reads and decrypts fingerprints / configurations (passive). | 4, 5, 6, 7, 8 | Required |
| **1** | **Injector** | Decrypts artifacts and inserts projections into AI sessions. | 4, 5, 6, 7, 8, 9 | Required |
| **1** | **Agent Consultant** | Issues consultation queries and applies the constrained signal. | 4, 6, 7, 8, 10 (incl. 10.5) | Required |
| **2** | **Fingerprint Producer** | Creates and updates fingerprints. | 4, 6, 7, 8 | Required |
| **2** | **Configuration Producer** | Creates and updates user configurations. | 5, 6, 7, 8 | Required |
| **—** | **Full Reference** | All of the above. | All sections | Required |

**Level 0 is the floor — and it requires no Phaedo cryptography, canonicalization, or schema machinery.** A client that reads `phaedo://fingerprint/projection` (the reference MCP server's plaintext resource) or accepts the `projection` field of a Section 9.3 response and inserts it gets Phaedo compatibility by consuming a string. The no-knowledge encryption envelope (§7) is a property of the *producer/vault* boundary, not a prerequisite for *consuming* a projection a user has chosen to surface. This is the "conformance in an afternoon" tier and the intended on-ramp for the broadest set of implementers (any MCP host already qualifies by reading the resource).

For Level 1 and above, conforming fingerprint, consultation request/response, and policy documents validate against the machine-readable JSON Schemas in `spec/schemas/` (the normative machine form). The reference conformance check is `spec/test-schemas.mjs`; fingerprint documents additionally validate with `spec/validate-fingerprint.mjs`.

### 11.2 Mandatory and Optional Features

Mandatory for **Projection Consumer (Level 0)** — and *only* these:

- Accept the Section 9.3 response `projection` string (standard mode), or read the `phaedo://fingerprint/projection` resource, and insert it into the session.
- Tolerate unknown fields in the response / resource payload (forward compatibility).
- Cryptography (Section 7), canonical serialization (Section 6), and schema validation are **NOT required** at Level 0 — the projection is consumed as text. A Level 0 consumer never holds an encrypted artifact, so it has no envelope to open.

Mandatory for **all profiles at Level 1 and above**:

- AES-256-GCM encryption envelope (Section 7)
- RFC 8785 canonical serialization for signing inputs (Section 6) — see the §6 implementation-status note for the v0.1 subset
- All required top level document fields (Section 4.1)
- Tolerance of unknown extension keys (Section 4.5)

Mandatory for Injector:

- All five v0.1 error codes (Section 9.5)
- Standard mode injection (Section 9.1)

Optional for v0.1:

- Enhanced privacy mode (Section 9.1)
- Asymmetric signatures (Section 8.3, deferred)
- Specific KDF tuning above the v0.1 minimum (Section 7.2)

### 11.3 Self Identification

A conforming implementation MUST publish a conformance statement listing:

- Profile(s) and level(s) claimed
- Protocol version supported
- Optional features supported
- Test vector results (Section 12)

The reference implementation publishes its statement at **`spec/conformance.json`** (machine-readable). It is kept honest by `spec/test-schemas.mjs`, which ties it to reality: the declared `protocol_version` must match this document's version, and the test-vector categories it reports as passing must match the populated vector sets in `spec/test-vectors/`. A third party publishes its own `conformance.json` in the same shape.

## 12. Test Vectors

> **Status (2026-06-15): live harness, partially populated.** Committed vectors live in `spec/test-vectors/*.json` and run against the reference implementation via `spec/test-vectors.mjs` (`node spec/test-vectors.mjs`; auto-run in CI). An external implementer runs the same vectors against their own producer/consumer to prove conformance. Vectors are regenerated from the reference impl, so any drift breaks the run.

Vector format (committed JSON; each vector carries its expected output so a third party verifies without trusting reference code):

```
{ "test_id": "T-PHAEDO-CANON-0001",
  "description": "...",
  "input": <input JSON>,
  "expected_canonical": <canonical string>,
  "expected_sha256": <hex> }
```

Test categories:

- **TC-CANON.** ✅ Populated — `canonicalization.json`. Locks the v0.1 `canonicalStringify` subset (§6 implementation-status note): key ordering, recursion, array-order, UTF-8, no-whitespace.
- **TC-FP-CONFORMANCE.** ✅ Populated — `fingerprint-conformance.json`. Good/bad §4 fingerprint documents checked by `spec/validate-fingerprint.mjs`; bad cases assert the reported error substrings. This is the good/bad corpus.
- **TC-CONS.** ✅ Populated — `consultation.json`. Deterministic resolver signal + deference for a fixed (fingerprint, request), with the §10.4 no-layer-content boundary asserted.
- **TC-ENV.** ✅ *Live (v0.1.47)* — `spec/test-vectors/envelope.json`. Unwrap-direction known-answer vectors (fixed key + §7.2 envelope → canonical plaintext) plus the integrity matrix: GCM tag tamper, §7.3 AAD (metadata) tamper, ciphertext tamper, wrong key — each MUST fail. Encryption is iv-randomized, so wrap-direction conformance is each implementation round-tripping its own output (still exercised by `scripts/test_envelope.mjs` + cross-impl `test_cross_compat.mjs`).
- **TC-EXPORT.** ✅ *Live (v0.1.47)* — `spec/test-vectors/export.json`. The §8.2 bootstrap export is fully deterministic (SHA-256 digest over the §6 canonical serialization with `digest` omitted), so the vectors are full known-answer objects — an implementation reproduces the export byte-for-byte, and the tamper vector proves an altered artifact cannot verify against the recorded digest.
- **TC-INJ.** ✅ *Live (v0.1.47)* — `spec/test-vectors/injection.json`. §9.2 request → §9.3 response invariants (required fields, layer selection) and the §9.5 error codes (`mode_not_supported`, `request_malformed`, `layer_not_available`, `decryption_failed`), exercised against the reference `buildInjectionResponse` over a fixed vault payload. `persona_strength_below_threshold` is declared but not triggered by the v0.1 reference (thresholding is consumer policy) — noted in the vector file.

Reference implementation MUST pass all populated vectors before tagging a release (enforced in CI via `scripts/test-all.mjs`).

## 13. Open Questions for v0.2

Tracked here so they are visible and resolved before v0.2:

1. **Enclave wrapped key format.** v0.1 leaves the wrapping format unspecified. v0.2 needs a normative format compatible with iOS Secure Enclave and Android StrongBox.
2. **Lock scope and key caching policy.** Phase 0 prototype work to drive a normative answer.
3. **Migration flow.** How a fingerprint moves between vault devices when the user replaces their phone.
4. **Locked fallback.** What an injection adapter does when the vault device is unavailable. Default behavior, user override, expiry of cached projections.
5. **User configuration scope expansion.** ✅ *Resolved (v0.1.42).* `domain` and `task` scope are normative: a scoped instruction carries its activation keys (`scope_domains` / `scope_tasks`, conditionally required by the schema) and activates per the §5.2 activation rules — deterministic consumers match fail-closed against `session_context.domain` / `task_hint` (or a consultation's `action_descriptor.domain`); model-mediated injection consumers without session context render the rule with an explicit conditional scope prefix. §9.2 `session_context` gains the optional `domain` field. Reference: `user-config.js instructionActiveFor` + `context-block.js renderOperatingRules`.
6. **Example corpus retrieval.** v0.1 says consumers SHOULD treat the corpus as a retrieval source. v0.2 may specify a normative retrieval API or reranking signal for examples.
7. **Configuration vs fingerprint conflict resolution.** ✅ *Resolved (v0.1.43).* The §4.7 "Effective resolution in context" specificity ladder makes authored-vs-inferred precedence exact at dimension granularity in a domain context: `authored_domain` > `authored_global` > `inferred_domain` > `inferred_global`, with a domain-bound rule never governing outside its domain, `unresolved` never falling through a tier, other-domain-tagged signals excluded in a known context, and deterministic within-tier tiebreaks. Reference: `resolveEffective()` (`extraction/resolve.js`); vectors `R-EFFECTIVE-*` (TC-RESOLVE).
8. **Cross encoder reranking signal.** Phase 1 work introduces reranking at injection time. The protocol may need a hook for the consumer to pass a rerank request alongside an injection request.
9. **Asymmetric signature scheme.** ✅ *Scheme resolved (v0.1.58) — **ES256, not Ed25519**.* §8.3 now specifies ECDSA P-256/SHA-256 with a non-extractable secure-element key. The revision off Ed25519 was forced by the custody requirement, not by preference: the iOS Secure Enclave holds P-256 only, so the previously-named algorithm could not coexist with "the key never leaves hardware", and custody is the property a third-party verifier actually depends on. Verified on device before specifying. **Still open:** (a) **key discovery for an UNPAIRED verifier** — publication, attestation and revocation are unresolved, which bounds §8.3 to parties that already share state; (b) the `signatures` entry shape and signature encoding, deferred until a consumer emits one, so the wire form is settled by a real use rather than in the abstract; (c) what else may be signed beyond a fingerprint (receipts, consultation responses — each is a distinct trust claim). Composes with OQ18/OQ19, which both assume a user-signed capability.
10. **Layer selection negotiation.** Does the consumer get a say, or is selection always producer driven? v0.1 chose producer driven; v0.2 may revisit.
11. **Consultation protocol formalization.** Move from sketch to normative for v1.0. *Progress:* `0001` abstain signal **folded v0.1.9**; `0003` authorizations (A-half) **folded v0.1.10**; `0005` `vd` contract **folded v0.1.12**; `0004` receipts **folded v0.1.13** (§10.6); `0002` Decision & Risk per-signal schema **folded v0.1.14** (producer emits + resolver consumes). Still queued: `0003` B-half (§5 home for authorizations, v0.2).
12. **Stained Glass interface stability.** ✅ *Resolved (v0.1.51).* §9.6 publishes the enhanced-privacy **interface** — the `privacy` response block (`profile`, `producer`, `preserved`, `removed`, `signal_retention`, `reversible`), five producer guarantees (no episodic content; no re-identification via examples; authored rules obfuscated or omitted, overriding §5.2 verbatim for this mode; honest layer accounting; **no silent downgrade** — refuse with `mode_not_supported` rather than emit plaintext), and a mechanical conformance check (structural, leakage, non-downgrade, example non-reproduction). The algorithm stays proprietary and out of scope, permanently. `signal_retention` is explicitly a self-assertion the suite does not verify.
13. **Per layer signal schemas.** ✅ *Resolved (v0.1.17).* The per-signal **shape** is now normative for **all eight layers** — `fingerprint.schema.json#/$defs/signal` (typed, bounded, enum `polarity`/`evidence_basis`), generalizing the Decision and Risk specialization in `decision-risk-signal.schema.json` (§4.2.7, `domain`/`threshold` reserved). The per-layer **field vocabulary** is published as a normative reference in `spec/layer-vocabulary.json` (generated from the reference producer catalog, tied by `spec/test-schemas.mjs`). Layer admission (§4.6) is now normative and enforced (no episodic content in behavioral layers). An unknown `field` remains tolerated (the vocabulary evolves); per-field `value` enums per layer are the remaining v0.2 tightening.
14. **Transport binding conformance.** `mcp-binding.md` is a draft transport binding. v0.2 should fold transport bindings into the conformance profiles (Section 11) and decide whether the MCP binding is normative for v1.0.
15. **Drift / change-point detection.** A behavioral model must distinguish a durable shift in a subject's pattern from a passing mood, and retire stale patterns (recency decay, change-point detection). v0.1 keeps `last_observed` for provenance only and applies no decay. Open: whether a normative recency/decay or change-point signal belongs in the resolver, or stays a producer-internal concern. Bites at scale; research track.
16. **Learning-loop integrity.** Corrections that update the fingerprint (delta annotations, agent-correction pairs) are not authenticated as genuinely the subject's, rate-limited only at the extraction-budget layer, and not anomaly-checked. An autonomous-agent future makes the *learning* surface (not just storage) a target. Open: what authentication / rate-limit / anomaly guarantees the protocol should require before a correction updates anything. Research track.
17. **Budget / blast-radius authorizations.** v0.1 §10.5 gates a single action by `amount_gt`. Long-running autonomous agents (Devin-style multi-day runs, agentic browsers, scheduled assistants) need standing **budgets** — `{amount, currency, window_hours, escalate_at}` carried on an authorization, decremented locally per resolved action, with `escalate_at` flipping the effect to `bias_cautious` and exhaustion flipping to `escalate`. Open: whether the running counter is a normative producer-internal artifact or a §10.6 receipt aggregate; window-reset semantics (rolling vs. fixed); how a budget composes with `agents` scope (per-agent budget envelopes). Roadmap target: v0.3. See `docs/roadmap/future-direction-2026-06-25.md`.
18. **Sub-agent capability tokens (scope snapshots).** When a parent agent spawns N children, N independent `phaedo_consult` calls are N× cost/latency AND a privacy expansion (every child re-pairs / re-derives). The future surface is a sealed, signed, time-bounded **scope snapshot** — "for the next 10 minutes, on these domains, magnitude ≤ medium, the answers are pre-baked as follows" — that a parent fetches once and hands to children. Composes with OQ9 (Ed25519): the parent's signature authorizes the scope; the child verifies. Open: scope grammar, revocation propagation when the underlying policy changes mid-snapshot, replay defense. Roadmap target: v1.0.
19. **Cross-agent delegated capabilities.** When agent A (vendor 1) hands off to agent B (vendor 2), B must reach the same fingerprint with bounded scope WITHOUT the subject re-pairing B from the vault. A **delegated capability** — user-signed, carrying `(delegating_agent, delegate_agent, domains, ttl)` — lets A authorize B for a slice of the consultation surface. Composes with OQ18 and with the §10.5 `agents` scope (RESERVED, blocked on authenticated agent identity). Open: revocation, transitive delegation (A→B→C: yes/no/depth-limited?), the audit chain on the §10.6 receipt. Roadmap target: v1.0.
20. **Voice / realtime capture binding.** Current capture covers chat surfaces only (the reference Chrome extension). The voice-agent class arriving 2026–27 (OpenAI Realtime, Vapi, Retell, Sesame, ElevenLabs Conversational) needs a binding spec: turn-taking signals, prosody/pace cues, interruption patterns → Surface / Behavioral / Collaboration & Relationship layer updates, honoring §10.4. Streaming-safe (no buffering of full conversation transcripts; deltas only). Open: the per-modality field vocabulary in `spec/layer-vocabulary.json`. Roadmap target: v1.0.
21. **On-device judge interface.** The reference resolver already supports an optional model-judge second pass beyond the deterministic resolver (`mcp/consult.js`). Specifying its interface as a normative *seam* lets third-party local models plug in — Apple Intelligence's on-device model, Qualcomm AI Hub, local Llama-class. Pure additive privacy gain: the judge stays local even when the calling agent is remote. Open: prompt shape, deterministic-fallback contract, judge-vs-resolver precedence (the resolver's `insufficient_signal` should not be silently overridden by a judge guess). Roadmap target: v1.0.
22. **Vault federation across devices (per-layer ACLs).** v0.1 assumes one vault per subject. A real user has a work device + a personal device; the protocol should accept **layered vaults** with per-layer authority objects ("work agents see `domain_and_expertise` + `temporal_and_context` only, never `big_picture`"). The Section 4.2 envelope already supports independent per-layer encryption — what is unspecified is the *authority* surface (who decides which layers a paired client sees). Open: canonical-vault resolution when layers disagree; whether the merge happens on the vault device or at consult time. Roadmap target: v1.x. Research-adjacent.
23. **Cross-fingerprint policy pre-flight (multi-party agent negotiation).** When two agents negotiate on behalf of two subjects (procurement: buyer's agent ↔ seller's agent; scheduling: two assistants; contract review: counter-party agents), each side needs to query the other's standing **authorizations** without learning persona content. `phaedo_check_authorization` extended to a counter-party endpoint, with a deterministic-only response and the §10.4 boundary preserved. The discovery layer (DID-style / DNS-style routing to a subject's oracle) is the missing piece, not the policy shape. Open: identity layer to bind to (W3C VC / DID, or a Phaedo-specific bootstrap). Roadmap target: v1.x. Speculative.

## Appendix B: Relationship to Other Standards

Informative.

- **OAuth 2.0 / OIDC.** Phaedo is to cognitive identity what OAuth is to authentication: a protocol that lets a user assert something to a third party in a verifiable, portable form, with the user controlling the canonical record.
- **W3C Verifiable Credentials.** Phaedo's signed fingerprint format (post v1.0) shares structural goals with VCs. v0.2 will evaluate whether the envelope can be expressed as a VC for interop.
- **JWE / JWS.** The envelope format is intentionally close to JWE in spirit but JSON object structured rather than compact serialization. v0.2 will evaluate alignment.
- **RFC 8785 (JCS).** Used directly for canonical serialization.
- **Model Context Protocol (MCP).** The primary transport binding for Phaedo's injection and consultation APIs, and the de facto integration standard for AI clients and agent frameworks. The Phaedo MCP server exposes the injection projection as an MCP resource and the consultation types as MCP tools. The binding is specified in `mcp-binding.md`; the core protocol remains transport-agnostic.

## Appendix C: Vault Data (`vd`) Contract

Informative. (Folded from proposal 0005; machine form: `spec/schemas/vault-data.schema.json`.)

`vd` is the decrypted runtime payload the reference consumers share — the object passed to `renderContextBlock(vd)` (injection, Section 9) and `resolveConsultationCore(vd, request)` (consultation, Section 10) by the content script, the harness, and the MCP server alike. It is a runtime convention, **not a wire artifact**: the normative artifacts remain the Section 4 fingerprint and Section 5 user configuration carried inside it.

| Key | Carries |
|---|---|
| `phaedo_fingerprint` | The Section 4 fingerprint document (including `consult_policies`, Section 10.5). |
| `phaedo_behavioral_signals` | Cross-session accumulated signals feeding the layers (producer-internal shape in v0.1). |
| `phaedo_linguistic_profile` | Surface/style features used by injection synthesis. No conversation content. |
| `phaedo_session_metrics` | Session counters / persona-strength inputs. No conversation content. |

All keys are optional. An object with no `phaedo_fingerprint` is a **legitimately empty vault** (a fresh user — nothing to render, not an error). A key present with the wrong type is a **contract breach** — a producer bug, distinct from emptiness.

Guard behavior at the consumer boundary (the reference implementation's policy, recommended for any consumer):

- **Fail loud in development:** name the violating field precisely (`validateVaultData` in `context-block.js`; `validateVaultShape` in the reference resolver).
- **Fail safe in production:** a breached payload skips injection (renders nothing, with a warning) or returns a structured error (`internal_error` naming the field) from consultation. A consumer MUST NOT resolve silently with partial data from a breached payload.
- Weird-but-conforming content (odd signal values, empty layers) is **not** a breach; consultation resolves it defensively (typically at low deference or as an `insufficient_signal` abstain).
